# Plan: "On Usage Limit" agent preference

Status: implemented on this branch; advisor-reviewed (§9); adversarial review findings adjudicated (§10). Target: choco-pi at 8ae02138, pi-coding-agent 0.87.1.

## 1. Feature

Add an "On usage limit" row to the Agent section of `/preferences` with three values:

| Value                | Token         | Behaviour when the active provider reports a usage limit                                                               |
| -------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| None (default)       | `none`        | Current behaviour: the run settles with the provider error; a notification names the provider and the estimated reset. |
| Fallback             | `fallback`    | Switch the session to a similar-tier model on another provider and continue the interrupted task.                      |
| Automatically Resume | `auto-resume` | Wait for the quota window to reset, then continue the interrupted task on the same model.                              |

Subagents: when a child session hits a usage limit, the child is recovered on a fallback model (default), the parent receives a structured notification naming the provider, the reset estimate and the substituted model, and the provider is closed for further spawns until the reset.

### 2.5 Existing recovery that must not be duplicated

`.pi/packages/choco-pi-goal` already implements provider-limit auto-resume, but only in goal mode: `recovery-runtime.ts:60-73` moves the goal to `paused` on `isProviderLimitError` and then schedules a fixed 5-minute retry (`runtime-config.ts:2`, `provider-limit-auto-resume.ts`). Because the goal is already `paused` by the time a later `agent_settled` handler runs, an "active goal" check cannot detect the goal runtime's ownership; the two runtimes need an explicit ownership contract (§3.3).

### 3.2 Classifier, corroboration and fallback table: `.pi/extensions/lib/usage-limit.ts`

`classifyUsageLimit({ provider, modelId, errorMessage })` returns `undefined` (not a limit) or `{ kind: "quota" | "billing" | "transient", provider, modelId, resetAt?, confidence: "structured" | "parsed" | "inferred" }`:

- openai-codex: `/Codex usage limit reached|hit your ChatGPT usage limit|usage_limit_reached/i`; `~N ?(m|min|h)` parsed as a lower bound (`parsed`).
- anthropic: `/^429\b|rate_limit_error/` → `quota`, `inferred`; the `Server requested (\d+)s retry delay` wrapper only supplies a candidate `resetAt = now + N s` when the wrapped message itself is a 429; on 408/409/5xx it yields `transient`.
- synthetic: `/^429:/` on provider `synthetic` → `inferred`.
- Anything matching the host non-retryable billing pattern (`insufficient_quota|billing|...`) is `kind: "billing"`, never auto-resumed, and only fallback-eligible. `transient` results are ignored by the controller.

`corroborate(ctx, classification)` upgrades or rejects `inferred` results using live account data: anthropic windows from `provider-usage.ts` (export a typed `providerUsageWindows(ctx, provider)`; today only report text is exported) with `percent >= 100`; synthetic via `SYNTHETIC_QUOTAS_REQUEST_EVENT` then `READ_EVENT`, treating any of `rollingFiveHourLimit.limited`, `rollingFiveHourLimit.remaining === 0`, `weeklyTokenLimit.percentRemaining <= 0` or a subscription quota at 0 as exhausted, each with its own reset timestamp; the earliest window that can restore capacity gives `resetAt`. An `inferred` result that cannot be corroborated is treated as transient: no auto-resume; fallback allowed once.

Fallback table `.pi/model-fallbacks.json` (validated with TypeBox, override at `~/.pi/agent/model-fallbacks.json`): tiers copied from §2.6. `pickFallback(current, { available, scoped, closed })` returns the first same-tier candidate on a different provider that is in `modelRegistry.getAvailable()`, allowed by `ctx.scopedModels` when non-empty, and whose provider is not closed; then secondary within tier; then Kimi-K3; else `undefined`. `model-guidance.md` gets a pointer to the JSON so both stay in sync.

Seam: `globalThis[Symbol.for("choco-pi.usage-limit-policy")]` is an owner-indexed map `Map<ownerId, Policy>` where `ownerId` is the root session id; each root extension instance registers on `session_start` and deletes its entry on `session_shutdown` and on reload (extension generation bump). The subagents manager looks up the policy for the root session that owns the child (it already knows the owning session for nested records). `Policy = { preference(), classify(), corroborate(), pickFallback(), closeProvider(key, until), isClosed(key) }`, structurally validated by the consumer like the existing `PREFERENCES_PROVIDER_SYMBOL` pattern. Closed-provider state lives inside the owner's policy, keyed by `(providerKey, accountId)` where `accountId` is the OAuth account id already derived in `provider-usage.ts` (`codexAccountId`, Claude/Synthetic equivalents) or `"default"` for API keys. The subagents package keeps its own `provider-health` registry for transient failures; usage-limit closures are consulted first and are authoritative until `until`.

### 3.3 Root controller: `.pi/extensions/usage-limit-policy.ts`

- Child inertness: the subagents runner sets a marker before `bindExtensions` (an `AsyncLocalStorage`-backed value published on the manager registry entry as `isChildSessionContext()`, or a session-level flag passed through `createAgentSession` options). The controller reads it on `session_start` and registers nothing else in children.
- Goal ownership contract: the goal package publishes `recoveryOwnership(): { goalId, status: "active" | "paused", providerLimitResumeScheduled: boolean } | undefined` on its registry entry (data already available via `goal-runtime-status.ts:15-23`). The controller yields whenever a goal exists in status `active` or `paused`, regardless of whether the goal regex matched; the goal package adopts the shared classifier from §3.2 in the same change so Codex prose and bare 429 are covered in goal mode too. This is in scope, not a follow-up, because otherwise goal mode silently loses the new behaviour.
- `agent_settled`: take the last assistant entry from `getBranch()`; ignore `aborted`; classify; corroborate; then:
  - `none`: `ctx.ui.notify` (when `hasUI`) with provider, reset estimate, `/model` hint.
  - `fallback`: `pickFallback`; `await pi.setModel(m)`; if false, next candidate; re-apply thinking level; `pi.sendMessage({ customType: "choco-pi-usage-limit", content: "<provider> usage limit reached (resets ~T). Switched to <m>. Continue the previous task without repeating completed tool calls.", display: true }, { triggerTurn: true })`. Recovery budget: at most 2 switches per interrupted task, tracked across generations; on exhaustion behave as `none`.
  - `auto-resume`: arm a wake-up at `min(resetAt + 30 s, now + 24 h)`; on wake, re-run corroboration and continue only when the readiness predicate holds (every exhausted window for the provider/account has reset, or the provider reports remaining capacity above zero); otherwise re-arm to the next reset. When `resetAt` is unknown, poll corroboration every 5 min for at most 6 h. On continue: same session id and generation, `ctx.isIdle()`, no pending messages, model unchanged since arming; then `sendMessage(... "Usage window reset; continue the previous task." ..., { triggerTurn: true })`. If the resumed turn hits the limit again, retry up to 3 times with the same rules, then notify and stop.
  - Persistence: `pi.appendEntry("choco-pi-usage-limit-pending", { recoveryId, resetAt, modelId, provider, accountId, attempts, branchEntryId })` when arming, and `pi.appendEntry("choco-pi-usage-limit-resolved", { recoveryId, outcome: "continued" | "cancelled" | "exhausted" })` on every cancel or completion, including user-turn and model-change cancellations. On `session_start` with reason `startup|resume`, scan `getBranch()` (custom entries are included, `session-manager.d.ts:304`) for the latest pending entry with no matching resolved entry, on the current branch, with `resetAt` in the future; only then re-arm. A process killed before `resetAt` loses the in-memory timer and relies on this replay; this limitation is documented.
- Cancel on `session_shutdown`, `session_start`, branch navigation, user turn (`before_agent_start` not originated by the controller), preference change, and user-originated `model_select` (controller-originated switches are tagged so they do not cancel themselves).
- Lifecycle: snapshot session id and generation before every `await`, recheck after each, per AGENTS.md.

### 3.4 Subagents

Principle (user decision, §6): the manager never switches a child's model on its own. A child's usage limit is reported to the parent agent, which decides (re-spawn or resume on another model). The only automatic behaviour is under the root preference `auto-resume`, where the manager parks the child and resumes it on the same model after the reset. The applicable preference for any child is the root preference; a mid-level subagent is "the parent" for its own children.

- `provider-health.ts`: add `closeUntil(providerKey, untilMs)` capped at 24 h; `recordFailure` unchanged for transient kinds.
- Runner: publish the child marker before `bindExtensions` (§3.3).
- `agent-manager.ts`, settle path after `classifyTerminalFailure`: call the seam. On `kind: "quota"` (or `"billing"`):
  - Preference `none` or `fallback`: settle as `error` as today, but attach `usageLimit = { provider, accountId, resetAt, kind, suggestedModel }` to the record; `suggestedModel` comes from the seam's `pickFallback` filtered by the parent's `scopedModels`, so the parent cannot be steered onto a disallowed model. Close the provider via `closeUntil(resetAt)`.
  - Preference `auto-resume`: new record status `waiting_for_reset` (not terminal; alongside `running|queued|completed|error|stopped`). Release the pool slot. Arm a wake-up at `min(resetAt + 30 s, now + 24 h)` with the same readiness re-check as the root (§3.3); unknown `resetAt` polls corroboration every 5 min for at most 6 h, then settles as `error` with the limit details. On ready: resume the same model through the original spawn path as a new generation. A second limit after resume settles as `error`. A foreground child is converted to background on limit: the caller's tool result returns immediately with `paused until T; result will arrive as a notification`, and the record's original promise is released. `stop_subagent`, parent session shutdown, `/reload`, and session switch cancel the wait and settle as `stopped`; the parent finishing its own turn does not.
- `resume(id, prompt, signal, { model? })`: new optional `model` argument (validated through `checkModelScope`, applied via `record.session.setModel`, auth throw → error result) so the parent can continue a limited child's context on another model instead of re-spawning. Exposed on the Agent tool's resume branch.
- Parent notification: exactly one final notification per task outcome, carrying a `usageLimit` block in `buildNotificationDetails` (provider, reset estimate, kind, suggested model or "none available", and for parked children the resume outcome). Under `auto-resume` an additional informational nudge `child <name> paused until T` is sent when the child parks. Emit `pi.events` `subagents:usage_limit` (informational, carries record id, provider, resetAt, status).
- `spawn()`, `drainQueue()`, `workflow.ts`: no automatic substitution. When the requested provider is closed by a usage-limit closure, return the existing `ProviderUnavailableError` message extended with the reset time and the suggested model, so the parent can choose.
- Nested: the same rules apply at every level; a mid-level subagent receives its children's notifications. Budgets are per record.
- Exclusions from parking (implementation decision, review-adjudicated): workflow nodes and side-conversation (`/btw`) records are reported, never parked, because their delivery is single-shot; worktree records and foreground `resume` runs do park. A parent record's terminal settlement still aborts its owned children (pre-existing upstream semantics); §6.6 "the parent finishing its turn does not cancel" refers to the parent's turn, not the parent record's end of life.
- No child-level preference row; `.pi/subagents.json` is unchanged.

### 3.5 Provider precision (optional, recommended)

- Codex: keep the human message and pass `resetAt` structurally instead of a prose token. Neither a non-enumerable error property (lost when the provider converts the error to the `errorMessage` string) nor a single global "last limit" slot (cross-session contamination) is acceptable as-is. The viable transport is for the codex provider extension to `pi.appendEntry("choco-pi-codex-usage-limit", { resetAt, planType, accountId })` in its own `message_end` handler when it observes its formatted limit message; the classifier then correlates by session branch and message timestamp. Verify in implementation that the codex extension has a session-scoped `pi` at that point; if not, this unit is dropped and Codex stays `parsed`.
- Synthetic: add a `message_end` handler in `extensions/provider/runtime.ts` that, on a `429` from provider `synthetic`, dispatches `SYNTHETIC_QUOTAS_REQUEST_EVENT` so the store is fresh when corroboration runs. Obtain a real limited-response body and header fixture before trusting anything above `inferred`.

## 4. Failure modes and mitigations

1. Transient 429 read as exhaustion (Anthropic, Synthetic): act only at `agent_settled`; require corroboration for auto-resume; fallback is allowed uncorroborated because it is cheap to reverse.
2. Rounded or partial resets (Codex minute rounding, Synthetic ticks, partial weekly regen): +30 s margin, bounded retries, terminal notification.
3. Fallback loops: per-task recovery budget carried across generations; Kimi-K3 is itself quota-limited, so a third limit ends in `none`.
4. Timer fires into the wrong state: session/generation guards, `isIdle`, pending-message check, cancel set in §3.3.
5. Subagent recovery racing settle: recovery scheduled after settle, never inline (§3.4).
6. Child identification too late: marker set before `bindExtensions` (§3.3), not a post-hoc registry scan.
7. Fallback lacks auth or is scoped out: `setModel` false → next candidate; scope re-checked.
8. Context shrink on fallback: existing `model-context-cap.ts` and compaction; one long-transcript switch test.
9. Global seam mixing sessions: closures keyed by provider+account and stamped with owner and generation.
10. Goal mode double-handling: controller yields whenever a goal is active or paused (ownership contract, §3.3).
11. Retry settings disabled: first 429 settles immediately; corroboration prevents treating it as exhaustion.
12. Synthetic body/header shape unknown: classification stays `inferred` until a fixture exists.
13. Wake-up before reset (reset > 24 h, or several blocking windows): wake re-checks readiness and re-arms; it never continues on a timer alone.
14. Persisted pending entry resurrecting cancelled work after restart: durable resolved entries written on every cancel; replay checks branch and recovery id.
15. Foreground child parked for hours: converted to background with an immediate tool result; resume re-enters the original spawn path.
16. Parent steered onto a disallowed model by the suggestion: `suggestedModel` is filtered by the parent's `scopedModels` and re-validated by `checkModelScope` on `resume`.

## 6. Decisions (resolved by the user before implementation)

1. Subagent usage limits are handled by the parent agent (re-spawn or `resume` with `model`); the manager does not substitute models. Under `auto-resume` the manager parks the child (`waiting_for_reset`) and resumes it on the same model after the reset. No separate child preference.
2. Auto-resume is a continuation message that triggers a new turn (no "retry last turn" API exists for extensions).
3. Codex reset metadata travels as a session-scoped custom entry appended by the codex extension; if that is not feasible, Codex stays `parsed`.
4. Synthetic classification stays `inferred` and quota-store-corroborated until a captured limited-response fixture exists.
5. `choco-pi-goal` keeps recovery ownership whenever a goal is `active` or `paused`; it publishes `recoveryOwnership()` and adopts the shared classifier in the same change.
6. Parked children: foreground converts to background with an immediate tool result; wait bounded at 24 h with re-arm; `stop_subagent`, parent shutdown, `/reload`, and session switch cancel; the parent finishing its turn does not. A caller-specified explicit `model` still auto-resumes on that model. Nested levels follow the same rules; a mid-level subagent is the parent for its children. Parent and child on the same limited provider need no special case. The tier table in `.pi/model-fallbacks.json` is the single source of "similar size".

## 7. Out of scope

Host changes to pi-coding-agent or pi-ai; changing Pi's retry policy; per-model (rather than per-provider) limit tracking beyond what the quota stores expose.
