# Computer-use end-to-end validation

The isolated harness is `CU/e2e/run.ts` (`CU/` means `.pi/packages/choco-pi-computer-use/`). Run it only from `/Users/Nebuleto/Workspace/choco-pi-dev`. It pins `/Users/Nebuleto/.local/pi-0.87.1/node_modules/.bin/pi` and refuses the 0.86.1 Homebrew launcher. Begin with:

```sh
node --experimental-strip-types .pi/packages/choco-pi-computer-use/e2e/run.ts --tier a --dry-run --preflight-only --baseline /tmp/choco-pi/$PI_SESSION_ID/e2e/baseline.json --waive-gate 'typecheck=pre-existing unrelated SDK mismatch' --waive-gate 'test=pre-existing subagent-config model expectation'
node --experimental-strip-types .pi/packages/choco-pi-computer-use/e2e/run.ts --tier a --baseline /tmp/choco-pi/$PI_SESSION_ID/e2e/baseline.json --main-daemon-pid 5914 --waive-gate 'typecheck=pre-existing unrelated SDK mismatch' --waive-gate 'test=pre-existing subagent-config model expectation'
```

To rerun a subset, add `--models <comma-separated ids>` and `--scenarios <comma-separated S-ids>` (default: all). A scenario filter must include `S1`: S1's isolation checks gate the other scenarios, so a filtered run cannot skip them. For example, `--models openai-codex/gpt-6-sol --scenarios S1,S3` runs S1 then S3 for that model only. Preflight still checks every configured model, and `summary.json` records the selection under `filters` (`null` for an unfiltered dimension).

The second command needs explicit authorization to spawn Pi and U2's fake wire daemon. Tier A is designed not to use Accessibility, Screen Recording, or live desktop input. Tier B requires separate authorization for a dev helper installation, signing/TCC, disposable fixture apps and desktop operation. No fallback model is implicit; pass `--substitute anthropic/claude-opus-5-5=<provider>/<model>` or the corresponding OpenAI id explicitly. Preflight errors exit 2 with a reason; an unavailable model includes the pinned-binary model-refresh command and substitution examples. A dry-run does not execute Pi, so version/model-list checks remain deferred; it does reject a non-pinned `--pi` immediately.

The baseline must contain a top-level `gates` object with `lint`, `fmt:check`, `typecheck`, and `test`; each is `0` or a non-zero code followed by a reason. Red gates block preflight unless individually named with repeatable `--waive-gate <gate>=<reason>`; unknown, duplicate, empty, or unnecessary waivers are rejected. A waiver does **not** change a failing root gate into a passing one. Preflight echoes each accepted gate, original status, and reason; `/tmp/choco-pi/<session>/e2e/summary.json` records them in `gateWaivers` for dry-run, preflight-only, and live runs. Do not infer a waiver from a baseline comment or silently waive a new failure.

Every evidence record must include this **Gate waivers** table, including an explicit “None” row when no waiver was used; entries must match the printed preflight output and `summary.json` exactly:

| Gate waivers | Baseline status                                                           | Explicit reason                                |
| ------------ | ------------------------------------------------------------------------- | ---------------------------------------------- |
| typecheck    | 1 (pre-existing: choco-pi-web-access + root tests/* SDK version mismatch) | pre-existing unrelated SDK mismatch            |
| test         | 1 (pre-existing: tests/subagent-config.test.ts)                           | pre-existing subagent-config model expectation |

For each attempt, preserve the run header (date, HEAD, Pi and Node versions), isolated agent/settings/symlink/socket proof, session JSONL and JSON-mode event path, daemon request log and optional holder/target fixture logs. Report every S1–S7 row per model as PASS, FAIL, INCONCLUSIVE, or BLOCKED with the first failed assertion or capacity reason. Never treat an unobserved step as PASS; tier B does not substitute for tier A.

## Scoring rules

`CU/e2e/assertions.ts` scores each scenario from the persisted session, the JSON-mode events, and the daemon request log. These rules apply:

- **Rejected before dispatch.** An `act_ui` error result without `details.execution` usually never reached the daemon (for example, a validation error such as "Coordinates require an image-bearing root", or a stale `observation_refresh_required` refusal). Policy and delivery rules do not score it. The harness checks instead that every `act`/`actBatch` request in the daemon log matches, by `requestId`, an executed result or a cancellation. Two exceptions apply. S7's harness-injected second-session act has no `requestId` and is excluded. S5's single act that the helper refused as `stale_look` is attributed to that refusal (see S5). An unmatched request fails the scenario with "rejected act_ui call may have dispatched". A non-error `act_ui` result without an execution trace also fails.
- **Per-step delivery.** When an execution has `steps[]`, each step must have `deliveryPolicy` `background` or `ax_only`, must not use `delivery:"hid"`, and must not have `escalatedToForeground`, `performed.activated`, or `performed.raised` set. Each step also needs matching `frontmostBefore` and `frontmostAfter` values. The aggregate is checked only for the fields it carries. An execution without steps must carry the fields itself.
- **Headless configuration.** Checked once per scenario over every CU result that carries `details.config` (`find_roots`, `observe_ui`, `act_ui`). It reports "headless config missing" when no result carries config (S4 is exempt) and "headless config incorrect" when any result has `headless` other than `false`.
- **INCONCLUSIVE(no_dispatch).** In S1, S2, S3, S4, and S6, when no `act_ui` call produced an execution and the daemon logged no `act`/`actBatch` request, the model never exercised the path under test. That scenario's dispatch assertions are skipped, and the verdict is `INCONCLUSIVE(no_dispatch)` if nothing else failed. It is never PASS and counts as not passing in `summary.json`. Any other failed assertion still makes the verdict FAIL.
- **S3 (didnt, no retry).** The daemon log has exactly one `typeText` act, and no `act`/`actBatch` follows it. No request uses `policy:"foreground"`, `foregroundGrant:true`, or `focusWindow`. No trace or step has `escalatedToForeground` or `escalationReason`. A `backgroundAttempt` may appear only with `outcome:"didnt"`: the bridge always records the refused background try this way on a background `didnt` (`attemptTrace`), so its presence is not a retry. The step whose `requestId` equals the typeText's must report `outcome:"didnt"`, or it or its trace must carry a `foreground_required` refusal whose `backgroundAttempt.outcome` is `didnt`. When the log records the helper reply (`response`), its `result.outcome` must be `didnt`. An earlier act in the same call (gpt-6-sol clicks the field first) is allowed. Since run 5 the S3 prompt names the `typeText` action on the field ref and forbids `setText`, because in run 4 gpt-6-sol used `setText`, which the fake answers `worked`.
- **S4 (cancellation).** The harness never signals Pi. The fake daemon holds the typeText past the TS transport timeout (`max(15 s, chars × 25 ms + 4 s)`, 15 s for the 400-character prompt). The transport then sends `cancel` for the act's semantic `requestId`. The log must contain a `cancel` row whose `target` equals the first typeText act's `requestId`, positioned after that act, with `ack:{acknowledged:true,state:"stopped"}`, and no `act`/`actBatch` after it. The act row's logged reply must be `error.code:"cancelled"`. One `act_ui` result must have `details.status:"cancelled"`, `details.error.code:"cancelled"`, `details.execution.outcome` `partial` or `rejected_before_delivery`, a numeric `execution.stoppedAt`, and `execution.cancel.state:"stopped"`. Pi must exit 0 and settle. S4's deadline is 5 minutes.
- **S5 (stale state).** The harness mutation (`fixtureMutation:"bump_root_generation"`) must be acknowledged (`ok:true`) and logged. No executed trace or step may report `outcome:"worked"`. Either of two refusal paths passes, and `notes.staleRefusal` records which one occurred. On the TS path (`observation_refresh_required`), no act follows the mutation and a result carries `observation_refresh_required` with reason `stale`. On the helper path (`stale_look`), exactly one `act` follows the mutation and was refused before delivery. The mutation bumps the fixture's root generation where the TS layer cannot see it, so the helper's look-id check refuses the act, as the native bridge does. Attribution is by the logged reply: `response.ok` is not true and `response.error.code` is `stale_look` (`attributedBy:"response"`). For logs without replies (run 3), attribution is by look id: the only rejected `act_ui` result says "Look id '<id>' is no longer available", and `<id>` equals that act's `lookId` (`attributedBy:"lookId"`). Any other act, a second act, or a different look id fails.
- **S6 (grant).** The daemon log has exactly one `policy:"foreground"` act, with `foregroundGrant:true` and an `ok` reply whose outcome is `worked` or `unknown`. `unknown` is expected: like the helper, the fake answers a granted HID click on a view without an AX action with `unknown`, because HID delivery cannot attest its effect. The act before it targets the same element, uses `policy:"background"`, and was refused with `foreground_required` and `effectPossible:false`. Exactly one executed trace step carries the foreground act's `requestId`. That step reports `escalatedToForeground:true`, `deliveryPolicy:"foreground"`, `foregroundGrant:true`, and the same outcome as the reply, and its trace reports that outcome too, so an `unknown` is never scored as a claimed change. Tier B applies the same cross-check (`CU/e2e/grant.ts`). The fixture's `Custom View` (`custom-1`, `AXGroup`, `canFocus`) stays a ref target, so no image is needed.
- **Isolation.** Only S1's isolation checks decide whether later scenarios run: the exact eight-tool allowlist, no unlisted tool call, no global agent path in the evidence, a scratch helper executable path, scratch-only settings packages, and no extension diagnostics on stderr. Failed isolation checks appear in S1's verdict with an `isolation:` prefix and block S2–S7 as `BLOCKED(isolation)`. If S1 never reached those checks (an exception, a capacity block, or an exhausted budget), S2–S7 are `BLOCKED(isolation-unproven)`. An S1 FAIL or INCONCLUSIVE with passing isolation checks does not block other scenarios.

Each `summary.json` verdict entry has informational `notes`: `actCalls`, `dispatchedActRequests`, `rejected_before_dispatch` (the index and error text of each rejected call), `reissuedAfterForegroundRequired` (`null` when no `foreground_required` refusal occurred), and, for S5, `staleRefusal`. Notes describe model behavior and never change a verdict. The S5 and S7 intervention reply is saved as `<scenario>.intervention.json` next to the request log.

`node --test CU/e2e/assertions.test.ts` replays tier-A evidence from 2026-09-23 stored in `CU/e2e/fixtures/<scenario>/<model>/`. It covers S1 from run 2 and S3 and S5 from run 3 (`/tmp/choco-pi/cu-u5c-9e686eaa/e2e`). Request logs and S1 stderr are verbatim. Events and sessions are sanitized: `message_update` streaming rows, `thinking` content blocks, and `signature`/`textSignature`/encrypted fields are removed. A test enforces this. For S1, opus scores PASS (two background acts and two calls rejected before dispatch), and gpt-6-sol scores `INCONCLUSIVE(no_dispatch)` (one rejected call and no dispatch). The S1 run's earlier FAIL verdicts and its S2–S7 `BLOCKED(isolation)` rows were scoring defects. S3 scores PASS for both models. S5 scores PASS for both via `stale_look`/`lookId`. Run 3 did not persist the mutation reply, so the replay supplies `ok:true`; the logged mutation and the helper's stale refusal support this. Run 3's S3 and S5 FAIL verdicts were scoring defects. Its S4 FAIL came from a harness defect: the harness sent SIGINT to Pi at `act_ui` start, before any act reached the daemon. S4 and S6 have no real-run fixtures yet, so synthetic evidence in the fake daemon's log shape covers their rules.

## Tier B (real helper, disposable fixture)

Tier B drives the real native helper against a disposable AppKit fixture on the live desktop. It needs separate authorization: an independently installed and signed dev helper, its TCC grants, and permission to operate the desktop. The harness neither installs nor signs the helper, and it never launches a helper daemon. It uses the dev daemon that is already running:

```sh
node --experimental-strip-types .pi/packages/choco-pi-computer-use/e2e/run.ts --tier b --baseline /tmp/choco-pi/$PI_SESSION_ID/e2e/baseline.json --helper-app /tmp/choco-pi/e2e-b/pi-computer-use.app --helper-socket /tmp/choco-pi/e2e-b/bridge.sock --main-daemon-pid 5914 --waive-gate 'typecheck=pre-existing unrelated SDK mismatch' --waive-gate 'test=pre-existing subagent-config model expectation'
```

Tier B requires both `--helper-app` and `--helper-socket`, and it refuses the main helper app or socket (`HELPER_IS_MAIN`). Preflight checks, in order: arm64, `codesign --verify --strict` on the app, the app's `source.sha256` against the committed arm64 prebuilt, and a live daemon on the helper socket. Before each scenario the harness checks the daemon directly: protocol 7, an executable realpath equal to the dev app's, and granted Accessibility and Screen Recording. It then claims and releases a harness session to prove that no earlier Pi session still owns the daemon; if one does, it waits up to 40 s, longer than the 30 s owner TTL. Tier B has no S7; S7 is tier A only.

**Request log.** The native helper keeps no request log. Pi's `PI_CU_SOCKET_PATH` therefore points to `<scratch>/b/bridge.sock`, where `CU/e2e/proxy.ts` forwards every byte unchanged to the helper socket. The proxy writes one row per request line in arrival order, using the fake daemon's shape: the request fields plus `origin`, `seq`, `at` (ms), and, once the request is answered, `respondedAt` and `response`. `cancel` rows also carry `ack`. Observation replies are reduced to `ok`, `error`, and the look id, so the log holds no outlines or images. The proxy's stdout and stderr go to `<scenario>.daemon.log`.

**Fixture.** `CU/e2e/fixture/FocusFixture.swift` is one `swiftc` binary, built by `CU/e2e/fixture/build.ts` into `<scratch>/b/fixture/<source-hash>/` and reused while the hash is unchanged. It is copied into two bundles:

- `CUFixtureTarget.app` (`com.choco-pi.FocusFixture`, window "CU Fixture Target", 640×480) has a text field labelled `Field`, an `Increment` button with a visible counter, and `Custom View`, an AX group whose `mouseDown` increments a second counter and which exposes no `AXPress`.
- `CUFocusHolder.app` (`com.choco-pi.FocusHolder`, "CU Focus Holder") has one text field. It stands in for the user's frontmost app.

Both apps append JSON lines to `$CU_FIXTURE_LOG`: `launched`, `appActive`/`appInactive`, `windowKey`/`windowResignKey`, `frontmost` (NSWorkspace activations), `fieldValue`, `increment`, `customHit`, `resized`, and `quitting`. `quitting` records the final field value, increment count, and custom-view hits. Only the holder logs `keyDown`. Neither app writes documents, defaults, or restorable state. Only the holder ever activates, once at launch. Each scenario attempt, including a capacity retry, gets a fresh pair and its own log directory, `<scenario>.attempt-<n>.<session id>.fixture/`. The harness refuses to launch into an existing directory, because a reused one would carry a stale `.cu-quit` (the new apps would quit at once) and earlier `launched` rows; every attempt's logs are kept. The harness starts the holder with `open -n`, then the target with `open -n -g`, so the target is never activated. It then requires that `lsappinfo front` names the holder, that the holder's log ends active, and that the target has never been active. If any check fails, the scenario is `BLOCKED(holder-not-frontmost: …)`; a fixture that fails to launch is `BLOCKED(fixture: …)`. A partial launch (for example, the holder started but the target did not) quits every instance already started before the scenario is reported, and any cleanup failure is appended as a `HARNESS_DEFECT`. After Pi exits, the harness stops the proxy and quits both apps (`.cu-quit` next to the logs, then SIGTERM, then SIGKILL, each bounded). It scores only after that. When the run ends, it removes the fixture bundles from LaunchServices with `lsregister -u`.

**Tier-B scoring** (`CU/e2e/tier-b.ts`) adds these checks to the tier-agnostic rules above: dispatch attribution, headless config, S1 per-step delivery and frontmost checks, and the S2 structured refusal. Tier A's S3–S6 daemon-script rules do not apply in tier B. The scoring window is the Pi process lifetime.

- **All scenarios except S6.** The holder log must show no `appInactive`, `windowResignKey`, or `keyDown`, and no `frontmost` event naming another app. Every act request must use `policy` `background` or `ax_only`, and wherever the helper reply reports both `frontmostBefore` and `frontmostAfter`, they must be equal.
- **S1.** Final field value `hello-e2e`, increment count 1, custom-view hits 0. The helper cannot attest an AXPress effect, so an `act_ui` result may say "Effect not verified for action N (press: unknown)" for the Increment press. Only `press` or `click` entries with outcome `unknown` are tolerated, and they are recorded in `notes.tierB.unverifiedEffects`. Any other entry (a `didnt`, or unverified typing) fails, as does an entry this rule cannot parse. The fixture's field value and counter remain the proof.
- **S2.** Custom-view hits 0. The generic S2 rule still requires exactly one act and a `foreground_required` refusal with `effectPossible:false`.
- **S3.** Exactly one `typeText` act and no act after it; earlier acts such as a field click are allowed and counted in `notes.tierB.priorActs`. Either the helper answered `worked` and the final field value is exactly `hello-e2e` (`typingPath:"worked"`), or it answered `didnt`/`foreground_required`, a result carries the structured refusal, and the field does not contain the text (`typingPath:"didnt"`).
- **S4.** The prompt (`scenarios/S4.b.txt`) asks for a 3000-character `typeText`. The TS transport timeout is `max(15 s, chars × 25 ms + 4 s)`, 79 s for 3000 characters. The real helper types about 12 ms per character (3.5 s for 300 characters, measured against the fixture), so it finishes long before that timeout fires. The proxy therefore sends the same `cancel {target: requestId}` if the typeText is still unanswered after 3 s, logged with `origin:"harness"`. This tests the helper's stop, acknowledgement, and no-input-after-ack behavior on real input. It does not test the TS timeout trigger; tier A covers that. Pass conditions: a `cancel` row whose `target` is the first typeText's `requestId` and that follows it; `ack.acknowledged:true` with `state:"stopped"`, or `stopping` when the act's own reply is `error.code:"cancelled"`; the act's reply is `cancelled`; no act after the cancel; no executed trace reports that request `worked`; and no fixture `fieldValue`/`increment`/`customHit` later than the ack's `respondedAt` + 50 ms. If the fixture logged no `fieldValue` before the ack, the no-input check proves nothing and the verdict is `INCONCLUSIVE(no_effect_observed)`.
- **S5.** After the first `observe_ui` result, the harness creates `.cu-resize`. The target moves and shrinks its own window and logs `resized`; the harness saves that acknowledgement as `S5.intervention.json` with `requestedAt` and `at`. The resize is out of band, so only the helper's window-frame check can see it. Exactly one act must follow the mutation, and its reply must be `ok:false` with `error.code:"stale_look"`, `effectPossible:false`, and the message "Window frame changed since look <id>; observe again". A generation `stale_look` ("Look id … is no longer available"), a second act, or no act fails. The fixture must log no `fieldValue`/`increment`/`customHit` after the resize. An act before the mutation fails as a harness race.
- **S6.** `PI_COMPUTER_USE_FOREGROUND_GRANT=com.choco-pi.FocusFixture` is set. The log must hold exactly two acts. The first uses `policy:"background"` without a grant and is refused before delivery with `foreground_required` and `effectPossible:false`. The second is the only `policy:"foreground"` act, has `foregroundGrant:true`, and has the same target and action. Its reply must be `ok` with outcome `worked` or `unknown`, where `unknown` is expected for HID delivery, and `frontmostAfter` must equal the target's pid. The execution trace must agree with that reply: exactly one trace step carries the granted act's `requestId`, and it reports `escalatedToForeground:true`, `deliveryPolicy:"foreground"`, `foregroundGrant:true`, and the reply's outcome, as does its trace; any mismatch fails. The fixture is the proof: custom-view hits exactly 1 and no `customHit` before the granted act. Activation is expected once the grant is used, so these holder rules replace the ones above:
  - A holder `keyDown` or `fieldValue` fails at any time, before or after the granted act; the grant never sends input to the holder.
  - A holder `appInactive` or `windowResignKey` earlier than the granted act's request time (`at`) fails. A granted act without a timestamp fails, and every holder focus loss then counts as early.
  - After the granted act, holder deactivation is expected, and at least one holder `appInactive` must fall within the Pi process lifetime.
  - Other holder rows, such as a `frontmost` event naming the target, are recorded in `notes.tierB.holderDisturbances` only.

`notes.tierB` in `summary.json` records the final fixture state, holder disturbances, `typingPath`, the S4 cancel origin and ack, and the S5 refusal path. `summary.json` also has a `tierB` block that names the helper app and socket, the proxy socket, the fixture hash, and the S4 cancel delay. `node --test CU/e2e/tier-b.test.ts` scores synthetic fixture and proxy logs for these rules, and checks the per-attempt fixture directory and the partial-launch cleanup with a fake `open`; it launches nothing.

## Process lifecycle and harness defects

Each scenario has a 4-minute deadline (5 minutes for S4), capped by the 30-minute model budget. When it fires, the harness sends SIGTERM to both Pi and the daemon, sends SIGKILL 2 s later, and moves on to the next scenario. Every wait after Pi exits is bounded by 5 s: Pi's exit, the S5/S7 intervention reply, draining Pi's stdout/stderr, flushing the event and stderr files, and stopping the daemon. A bound that expires does not hang the run. The scenario verdict gets a `HARNESS_DEFECT(...)` suffix instead, and a verdict that would otherwise be PASS becomes `FAIL(HARNESS_DEFECT(...))`. A harness defect is a harness fault, not a model result. The daemon never inherits the harness's stdio. Its stdout and stderr go to `<scratch>/<tier>/<model>/<scenario>.daemon.log`.

As each scenario finishes, the harness prints `<tier> <model> <scenario> <verdict>` and rewrites `summary.json` with the verdicts so far (`status: "running"`). If an exception ends the run, it writes `status: "ABORTED(<reason>)"` and keeps the verdicts recorded so far. A `summary.json` still marked `running` with no process alive means the harness was killed externally.

The 2026-09-23 tier-A hang happened because `launch` piped Pi's stderr into its file with `pipe()`. The pipe ended the file stream at stderr EOF, so the stream's `finish` event could fire before the harness called `once(err, "finish")`, and that wait never resolved. `node --test CU/e2e/process.test.ts CU/e2e/launch.test.ts` covers this case, a Pi that ignores SIGTERM, and a descendant that holds Pi's pipes open. The tests use dummy Node children and never spawn Pi. The root `pnpm test` glob does not include `CU/e2e/`, so run these tests explicitly.
