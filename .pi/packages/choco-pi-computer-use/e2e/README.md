# Computer-use E2E harness

Run from the dev worktree only. `node --experimental-strip-types .pi/packages/choco-pi-computer-use/e2e/run.ts --tier a --dry-run --preflight-only --baseline <path>` prints the exact isolated Pi commands, symlink targets, env and artifact paths without spawning Pi. `--pi /opt/homebrew/bin/pi` must fail with `PI_VERSION_MISMATCH` (exit 2). A live run requires `--baseline <path>` with root-gate evidence, a fake daemon at `CU/tests/helpers/fake-helper-daemon.ts`, and authorization to spawn Pi. The fake daemon is supplied separately by U2; until then the tier-A launcher refuses with `FAKE_DAEMON_MISSING`. No installer, signing, or permission request is made here.

`--models <ids>` and `--scenarios <S-ids>` take comma-separated lists and default to all. A model filter entry may name the configured id or its `--substitute` target; unknown or duplicate ids exit 2 with `ARGUMENT`. A scenario filter must include `S1`, because only S1's isolation checks decide whether later scenarios run; scenarios always run in S1–S7 order. Preflight still checks both configured models. `summary.json` records the selected `models` and `filters: {models, scenarios}` (`null` when unfiltered).

The baseline's top-level `gates` object must name `lint`, `fmt:check`, `typecheck`, and `test`. A non-zero status requires an explicit, repeatable `--waive-gate <gate>=<reason>` for that exact gate; passing gates cannot be waived. Each accepted waiver is printed and recorded with the original red status in `<scratch>/summary.json`. Evidence reports must reproduce these entries in a **Gate waivers** table, even if the table says “None”. See `docs/computer-use-e2e.md` for the format. A waiver records an out-of-scope red gate; it does not claim the gate passed.

Tier A daemon CLI contract: `node --experimental-strip-types tests/helpers/fake-helper-daemon.ts --socket <scratch>/a/bridge.sock --script S1..S7 --log <scratch>/a/<model>/<scenario>.requests.jsonl --executable-path <scratch>/a/pi-computer-use.app/Contents/MacOS/bridge`. It serves newline-delimited JSON request/response envelopes, protocol 7 diagnostics and granted permissions, and logs each request with `cmd`, `id`, `session`, `policy`, and `foregroundGrant`. It logs `act`/`actBatch` rows when it answers them, adding `response` (the reply without `id`). It logs `cancel` rows as `target` (the act's `requestId`) plus `ack:{acknowledged,state,stoppedAt,effectPossible}`. It must simulate `foreground_required`, `didnt`, cancellation and ownership in their respective scenarios. In S4 it holds the typeText past the TS transport timeout, and the transport's own `cancel` stops it; the harness never signals Pi. The harness sends a second-session `act` after the first primary action in S7 and a mutation `look` request with `fixtureMutation:"bump_root_generation"` in S5. U2 confirmed this control field. The fake reports the supplied executable path in diagnostics for S1 isolation checks. The harness spawns it with `stdio: ["ignore", "pipe", "pipe"]`, drains both streams to `<scenario>.daemon.log`, and stops it with SIGTERM, then SIGKILL after 2 s, waiting at most 5 s. `process.ts` holds the bounded wait helpers and `launch.ts` holds the Pi runner. `process.test.ts` and `launch.test.ts` test them with dummy children and never spawn Pi.

Tier B (`--tier b --helper-app <dev app> --helper-socket <dev daemon socket>`) needs explicit authorization for the desktop, an independently installed and signed dev helper, and a dev daemon that is already running with TCC granted. The harness never installs, signs, or launches a helper and refuses the main helper app or socket. Pi connects to `<scratch>/b/bridge.sock`, where `proxy.ts` forwards bytes unchanged to the dev daemon and writes `<scenario>.requests.jsonl` in the fake daemon's row shape (`origin`, `seq`, `at`, `respondedAt`, `response`, `ack`). In S4, the proxy cancels a typeText still in flight after 3 s (`origin:"harness"`), because the real helper finishes before the TS transport timeout. `fixture/FocusFixture.swift` (built by `fixture/build.ts` into `<scratch>/b/fixture/<hash>/`; no binary is committed) provides the disposable target (`com.choco-pi.FocusFixture`: Field, Increment, and a Custom View without AXPress) and holder (`com.choco-pi.FocusHolder`) apps. `desktop.ts` launches the holder, then the target without activation, proves that the holder is frontmost, performs the S5 `.cu-resize`, and quits both apps. Each app logs to `<scenario>.attempt-<n>.<session id>.fixture/{target,holder}.jsonl`, a fresh directory per attempt. `tier-b.ts` scores S1–S6 from those logs and the proxy log; `tier-b.test.ts` covers it with synthetic logs. Rules are in `docs/computer-use-e2e.md` under “Tier B”. Never run tier B against TextEdit, Notes, or user documents. The harness does not call `registerPermissions` or `openPermissionPane`.

Evidence is written under `/tmp/choco-pi/<PI_SESSION_ID>/e2e/{sessions,a/<model>,b/<model>}`. A run report must name date, revision, Pi/Node versions, scratch and isolation proof, scenario PASS/FAIL/INCONCLUSIVE/BLOCKED with session/event/request/fixture log paths, and failures/deviations. These are machine-checked verdicts, not summaries of model prose. Never publish or attach full-screen captures or credentials. Scoring rules (rejected-before-dispatch calls, per-step delivery, once-per-scenario headless check, `INCONCLUSIVE(no_dispatch)`, isolation-only blocking) are in `docs/computer-use-e2e.md`; `assertions.test.ts` replays recorded S1, S3 and S5 evidence in `fixtures/<scenario>/<model>/`, where events and sessions are stripped of streaming deltas, thinking blocks and signatures. It also scores synthetic S4 and S6 evidence in the fake daemon's log shape. The S5/S7 intervention reply is saved as `<scenario>.intervention.json`.
