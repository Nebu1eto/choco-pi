# choco-pi-computer-use

Vendored, private fork of [`@injaneity/pi-computer-use`](https://github.com/injaneity/pi-computer-use) for the choco-pi harness. It keeps the upstream tool names and TypeScript source layout, and pi loads `extensions/computer-use.ts` directly without a build step.

## Platform support

This fork supports native helper installation on macOS only. The Linux and Windows TypeScript backends remain for dispatch compatibility, but their native helpers, prebuilts, and build paths are not included.

No helper binaries are tracked. `scripts/setup-helper.ts` compiles `native/macos/{agent_cursor,agent_cursor_motion,bridge}.swift` for the host architecture with `xcrun swiftc -target <arm64|x86_64>-apple-macosx14.0 -O` into a scratch directory under the system temporary directory, then wraps, signs, and registers the app bundle. At runtime, a UI session setup or tool operation checks the helper; if it is missing, `src/platform/macos/helper.ts` launches the script.

### Installing

- Requires the Xcode Command Line Tools (or Xcode), which provide `xcrun swiftc`; install them with `xcode-select --install`. Without `swiftc`, the script fails and says so.
- A build takes tens of seconds (about 13 s on Apple silicon with a cold module cache). Compiler warnings are printed and do not fail the build.
- The bundle's `Contents/Resources/source.sha256` is `helperSourceHash` from `src/platform/macos/helper-source.ts`: sha256 over the scheme tag, the architecture, and each compiled Swift source's relative path, byte length, and contents. When it and `Info.plist` match, the script skips the build and leaves the installed helper unchanged.
- `--arch arm64|x64` overrides the host architecture. Cross-compilation (x64 on Apple silicon or the reverse) is untested.
- `--build-only --out <dir>` writes `<dir>/bridge` and installs, signs, and registers nothing.

The installer may modify `/Applications` or `~/Applications`, register the app with LaunchServices, and codesign it. Do not run it during static validation.

## Helper protocol and test environment

The TypeScript client requires helper protocol 8: request cancellation, cross-process sessions (see Sessions and concurrency), native enforcement of the foreground grant, and since protocol 8 owner-checked cancels, relative deadlines, and a verified focus restore. The Swift sources implement protocol 8. A daemon that reports another protocol is shut down and relaunched once. The daemon outlives Pi and reinstalls, so it is also relaunched once when it runs from another executable path, reports no `startedAt` (a helper built before that field existed), or started before the installed executable's last modification (a same-protocol rebuild); the error names the reason if the relaunched daemon is still stale. Cancelling a browser tool call stops the remaining actions in its batch and releases any pressed key or mouse button.

Protocol 8 wire changes: `act` and `actBatch` send `budgetMs`, a relative time budget, and the helper takes the deadline from its own monotonic clock when it receives the request (an absolute `deadlineMs` is refused with `invalid_args`); owner TTL and cancel tombstones use the same clock. `cancel` carries the caller's `session`; the helper refuses (`not_request_owner`) to cancel, report on, or tombstone a request registered by another session, and a request registered without a session keeps the old behavior. `getFrontmost` reports the frontmost app's focused window, else its main window, with `windowId`, `windowRef`, and `windowSource` (`focused`, `main`, or `unknown`, in which case no window is reported). `restoreUserFocus` takes `windowRef`, `windowId`, `windowTitle` (used only without the other two), and `expectedFrontmostPid`: if that pid is no longer frontmost it changes nothing (`reason: frontmost_changed`). It returns `appRestored` and `windowRestored`, each verified after the change. Every error of a granted HID `act`, or of an `actBatch` with such a step, carries `inputSent`: `false` for a refusal before the request was registered (ownership, arguments, a duplicate id), otherwise from the helper's count of events the request posted, including a cancel or deadline at its first checkpoint.

Every request that addresses a window, pid, or element for observation or input (`look`, `act`, `actBatch`, `axWaitFor`, `axReadText`, `hitTest`, `focusedElement`, `focusWindow`, `setWindowFrame`, and `getUserContext`) may carry `appBlocklist: {bundleIds, pids, clientPid}`, and the client sends the effective blocklist of the tool call (the policy it loaded when the call started) on each such request it makes, with its own pid as `clientPid`. With `clientPid`, the helper walks that process's ancestry itself, from the kernel's process table (no subprocess), up to launchd, and refuses every ancestor as if it were listed in `pids` (`blockMatch: pid`). When the walk cannot complete (a lookup fails midway, for one because a process exited between steps, the chain loops, or it passes 4096 processes), the helper refuses every owner the request addresses with `app_blocked`, `blockMatch: unknown_ancestry`, and `unknownAncestryOf` (the client pid), instead of deciding with a partial list. A request without `clientPid` is checked as before. The helper resolves the real owner and refuses a listed pid or bundle id, and always its own process, with `app_blocked`: `effectPossible: false`, `inputSent: false` for acts, and `blockedPid`, `blockedApp`, `blockedBundleId`, and `blockMatch` (`pid`, `bundle_id`, `helper`, `unknown_owner` when bundle ids are listed and the owner's identity cannot be resolved, or `unknown_ancestry`). The refusal comes before any capture, AX tree walk, activation, AX write, or event post. Root and app listings are not filtered. `getFrontmost` and `restoreUserFocus` are not checked, since they only report or give focus back to the user's app. `diagnostics.invariants` includes `owner-checked-app-blocklist` and `local-pointer-evidence` on a helper with this check and the three-way pointer rule (see Foreground grants), `client-ancestry-blocklist` for the ancestry walk, `hid-input-sent-on-every-error`, `observed-window-destination` and `post-release-destination-check` (see the destination check), `path-segment-pointer-evidence` (the drag region), and `editor-text-commit` (see Action results). The helper trusts the list and the client pid the client sends, so another local client can send an empty list or another pid.

### Sessions and concurrency

One helper daemon serves every Pi process on the machine (one socket), and since this change it serves any number of sessions at once. A session is one Pi process: every request carries its `session {id, generation}` (all module instances and Pi sessions of a process share it, and the TypeScript scheduler and foreground section serialize them inside the process). The helper keeps per-session state and enforces the cross-process rules itself, because the TypeScript locks only cover one process. The protocol stays 8: the changes are additive (new codes, the `foregroundSection` command, `diagnostics.sessions` and `diagnostics.inputSource`, invariants `multi-session`, `per-target-serialization`, `exclusive-foreground-section`, `session-scoped-looks`, `layout-independent-text`, `verified-text-entry`, `pid-key-destination-check`, and `looks-outlive-liveness`). A protocol-8 client written for the single-owner helper keeps working against this helper (it is simply never refused for another session), and this client keeps working against a single-owner protocol-8 helper: it only uses the foreground section and claims at observation time when `diagnostics.invariants` lists `exclusive-foreground-section`, and it still maps `owned_by_other_session` to a structured result. The restart-on-mismatch path is unchanged; a `shutdown` is refused with `helper_busy` while another session has a request in flight, so a client restarting the helper never cuts another session's input off half-way (its restart then simply finds the same daemon).

- **Liveness.** Any request registers its session. Each session has its own TTL (30 s since its last request) and is pinned live while it has gated requests in flight. A session that crashed or stopped sending expires alone: a foreground section it held is released (focus given back as below), it no longer counts as live or busy, and other sessions are unaffected. Liveness expiry does not drop its looks (see the next item). Per-app holds belong to a request and end with it, so a quiet session holds none. Within one session id the single-owner generation rules remain: an older generation is refused, and a newer one is refused while the older still has requests in flight (`owned_by_other_session`, now only for that case).
- **Looks and refs.** A look (and the element and window refs it hands out) belongs to the session that made it. Another session's `lookId` is refused with `not_look_owner` (nothing sent); another session's refs resolve to nothing. Each session keeps its own 8 most recent looks, so other sessions' observations never evict a session's look while it waits for the helper. The client sends nothing between tool calls, so a model that thinks, or a user who answers a dialog, for minutes would otherwise come back to an expired session: looks are kept apart from liveness, and a session that returns with the same id and generation finds them (the helper's checks of the window and element still apply on use). They are reclaimed by `release`, by a newer generation of the same id (a look is usable only by the generation that made it), when the client process its requests named (`appBlocklist.clientPid`) no longer exists, after an hour of silence when no client pid is known, and, beyond 64 sessions with looks, least recently used first. That bounds the helper to 512 session look records (8 × 64; a record is a few hundred bytes and one accessibility element reference, no image). The helper looks for gone sessions at most every 5 s and never reclaims a session heard from within the TTL. `diagnostics.sessions.looks` reports `sessions`, `records`, `perSession`, `maxSessions`, and `retentionWithoutClientMs`.
- **A look that is gone.** When the helper refuses the first act of an `act_ui` call with `stale_look` before sending anything (the look was reclaimed, or the window changed since it), the result is not a bare error. Its text is the `observation_refresh_required` requirement the TypeScript layer gives for a stale state (`reason: "stale"`, the `observe_ui` call to make in `refresh`, and `cause` with the helper's code and message), and `details` has `status: "observation_refresh_required"`, `nextStep: "observe_then_retry"`, `refresh`, and an execution whose step carries the refused request's `requestId`. A `stale_look` at a later action stays a `partial` result.
- **Acts on one app.** Every `act`, `actBatch`, `focusWindow`, and `setWindowFrame` holds its target pid for its duration: acts on different apps run concurrently, acts on one app are serialized across all sessions and processes. A request that cannot get its app within 10 s (or its own budget) is refused `target_busy` with `inputSent: false`; `act_ui` answers `details.status: "target_busy"`, `nextStep: "retry_later"`, and keeps the state_id usable.
- **Two windows of one app.** Background (`pid`) key events go to the app's key window, whatever window an Accessibility focus change addressed (measured: with window 1 key, keys for a focused field of window 2 landed in window 1). Before the first key of a standard-delivery `keypress` or key-typed `typeText`, the helper requires the app's key window and focused element to be in the observed window (and the focused element to be the act's element); otherwise nothing is sent: `key_window_conflict` (`retry_later_or_other_window`) when the focus is provably in another window, else `foreground_required`. Text into a native field does not use key events (see Action results), so it reaches the addressed window's field even when that window is not key. Extended delivery makes the observed window key before any key and refuses when it does not become key, as before.
- **Foreground (HID) delivery.** The helper has one exclusive foreground section. A granted HID act, and `focusWindow` or `restoreUserFocus` with a grant, run inside it; the TypeScript client takes it explicitly (`foregroundSection {op: acquire, waitMs}`) for its whole foreground call, from capturing the user's focus through the restore, and releases it afterwards (`op: release`). While another session holds it, a foreground request waits up to 10 s and is then refused `foreground_busy` with nothing sent (`act_ui` status `foreground_busy`, `retry_later`). A section whose holder sent nothing for 10 s, or whose session expired, is released by the helper, which first gives focus back to the app and window recorded at acquire when one of the section's targets is still frontmost. Background acts of other sessions keep running during a section, except on an app the section has driven in the foreground: that app is frontmost with the holder's focus, so they wait (`target_busy` at the bound).
- **Extended delivery.** The synthesized activation stays counted per target pid across sessions; acts on one pid are serialized anyway, and shutdown still deactivates every active target.

| What the single owner guarded           | Rule now                                                                                                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cancel routing                          | Unchanged: only the session that registered a request may cancel or ask about it (`not_request_owner`).                                                           |
| Look ids and refs                       | Per session; another session's look is refused `not_look_owner`, its refs resolve to nothing.                                                                     |
| Interleaved input of two sessions       | Per-target serialization for every act; one exclusive foreground section for HID input.                                                                           |
| The foreground grant                    | Still per request (`foregroundGrant`); the section decides who may use the foreground now.                                                                        |
| Foreground restore                      | Done by the section holder inside its section before release; an expired section is restored by the helper.                                                       |
| `release`                               | Ends only the caller's session (its looks, its section); refused `owner_busy` while that session has requests in flight; never affects other sessions.            |
| `release` while another session is busy | Allowed; the other session continues.                                                                                                                             |
| `shutdown`                              | Refused `helper_busy` while another session has requests in flight.                                                                                               |
| Diagnostics                             | `diagnostics.sessions` (live sessions, requests in flight, whether the section is held, busy targets) and `diagnostics.inputSource`; no session ids are reported. |

- `PI_CU_SOCKET_PATH` points the client at another helper socket. With it set, the client never installs or launches the helper app.
- `PI_COMPUTER_USE_HELPER_APP_PATH` overrides the helper app bundle whose executable `diagnostics.executablePath` must match.
- `tests/helpers/fake-helper-daemon.ts` serves the protocol without touching Accessibility, screen capture, or input: `node --experimental-strip-types tests/helpers/fake-helper-daemon.ts --socket <path> --script <s1-ok|s2-foreground-required|s3-didnt|s4-slow-type|s5-stale|s6-grant|s7-ownership|s8-foreground-not-acquired|s9-foreground-lost|s10-pid-unknown> [--log <requests.jsonl>] [--executable-path <path>] [--protocol-version <n>] [--started-at <epoch-seconds|none>] [--user-app terminal|neutral]`. `--user-app` sets the identity of the fake's frontmost user app (pid 4141): `terminal` (default) is Terminal, which the blocked-app policy refuses; `neutral` is an app it allows. Tests import `startFakeHelperDaemon` from the same file; it also takes `secondTarget`, `foregroundHoldMs`, `targetKeyWindowId` for the concurrency and window-restore tests, and `realOwner` (`window` or `element`), which makes the user app the real owner the fake enforces `appBlocklist` on. `s10-pid-unknown` answers a background pid click on the custom view with `unknown` and outside-target evidence. `extendedDelivery` (`available` or `unavailable`) adds the capability to diagnostics and answers acts that ask for extended delivery like the helper; `extendedAnswer` (`unknown`, the default; `ending` and, for a typeText, `key_window_refusal`, the helper's answers to an act that ended after the activation; or a misbehaving `foreground_required`, `foreground_required_bare`, or `didnt`) is how a used one is answered, so `tests/background-delivery.test.ts` can prove the client never delivers it a second time. ## Blocked apps

Computer-use never observes or operates the app hosting Pi (this process's ancestors, and the bundle id in `__CFBundleIdentifier`), terminal emulators (Terminal, iTerm2, Warp, kitty, Ghostty, Alacritty, WezTerm, Hyper, Tabby), password managers (1Password 7 and 8, Bitwarden, Passwords, Keychain Access), the macOS authentication dialog (`com.apple.SecurityAgent`), or the helper. The block covers every tool and delivery policy, including `ax_only`, and is decided before any capture or input request. A tool call decides with the configuration it loaded when it started, even if another session loads a different project's configuration meanwhile. If the lookup of this process's ancestors fails, only this process and its parent are blocked on the TypeScript side, the lookup is retried on every later tool call, and the helper's own ancestry walk (`clientPid`) still refuses every ancestor. A refused call fails with `app_blocked`, and `find_roots` marks such roots `blocked: true` with `block_reason`. `blocked_apps` (`PI_COMPUTER_USE_BLOCKED_APPS`) adds bundle ids from any source, and the lists of all sources are combined. Only `unblocked_apps` in the user config file lifts a default block. Unblocks from the project file or the environment are ignored and shown as ignored in `/computer-use`, and the host app and the helper cannot be unblocked.

The helper re-checks the real owner of the window or element: the window server's owner of the window id, the accessibility owner of the element (again for the element actually resolved at delivery time), or the frontmost app on implicit-focus paths, together with that process's bundle ids. A refusal there reads the same as the TypeScript-side one.

## Foreground grants

Input goes to the target app in the background. Pointer input that has no accessibility route (a click on a native element without `AXPress`, or a coordinate click, scroll, or drag) is first posted to the app's process without activating it or moving the cursor. The helper then watches a settle window of at most about 400 ms and decides one of three outcomes (`deliveryUsed: "pid_pointer"`, `pidPointerAttempted: true` in every case):

- `worked`: a change specific to the target. That is the element's value, selection, frame, or scroll position, the element under the point (only when it is still the target's), the target app's focused element, focused window, sheets, or onscreen windows, the target itself becoming the frontmost app, or, with Screen Recording, pixels inside the target region. The target region is the element's frame plus 8 pt, or for a coordinate a 64 × 64 pt square centered on the point; for a drag, such squares centered on the path's points and on points at most 32 pt apart along each of its segments, never their bounding box, the act's separate target point, or the element's frame (only the points the drag posts). The region is clamped to the window. The pixels come from a downsampled capture of the window compared with one taken just before the input (`evidence.pixelChange: true`).
- `unknown`: nothing target-specific changed, but pixels outside the target region did (`evidence.changeOutsideTarget: true`, `pixelChangeOutsideTarget: true`, `observableChange: false`). The click may or may not have done something, so the result says the effect is not verified. It is never retried, never escalated to the foreground, and asks for no grant.
- `foreground_required`: nothing changed anywhere. The evidence is `observableChange: false` and `pixelCheck` (`compared` or `unavailable`).

Another app becoming frontmost during the settle window is not evidence of the click. It is recorded as `evidence.frontmostChangedElsewhere: true` with `frontmostChangedTo` (that app's pid). The evidence also carries `pixelRegion` (`element`, `point`, or `outside_window`), `pixelRegionPoints` (the bounding box of the region, for reference), and `pixelRegionParts` (how many squares or frames it is made of). Animation inside the target region itself (a blinking caret, an animated button) can still produce a false `worked`. Other actions that need focus (pointer input on web content, some keyboard input) are refused before any delivery. A refused action needs the user to grant foreground delivery for that app. No tool parameter can grant it. Grants come from:

- `foreground_grant` (bundle IDs or `"*"`) in `~/.pi/agent/extensions/pi-computer-use.json` or `<cwd>/.pi/computer-use.json`, or `PI_COMPUTER_USE_FOREGROUND_GRANT`. File edits apply on the next tool call.
- Session grants, decided by `foreground_prompt` (`PI_COMPUTER_USE_FOREGROUND_PROMPT`) when the helper refused a background attempt and either proved nothing was delivered or saw no change after a background pointer attempt:
  - `ask` (default): in an interactive TUI session, Pi asks once per app per session: **Allow for this session**, **Always allow (saves to user config)**, or **Not now**. "Always allow" also appends the bundle ID to `foreground_grant` in the user file and keeps every other key; if saving fails, the grant still applies for the session and Pi says so. "Not now" stops further prompts for that app this session. Other host modes are never prompted.
  - `always`: explicit opt-in to full approval. The app is granted for the session without a dialog, in every host mode, even after an earlier "Not now".
  - `off`: never prompts.

After a grant, a refusal that proved nothing was delivered is retried once in the foreground. The trace records `escalationReason`: `foreground_required` (a file, env, or earlier session grant), `user_grant` (the dialog), or `auto_grant` (`always`).

A refusal after a background pointer attempt is never retried in the same call, whatever the grant, dialog answer, or `always` says: the input already reached the app, and a change the helper could not see would otherwise happen twice. The grant is still recorded (and "Always allow" still saved). The result carries `details.nextStep: "observe_then_retry"`, `refusal.grantedForNextCall`, and `execution.retryDeferred`, and tells the model to call `observe_ui` before acting again. With a grant, the next pointer-only click, coordinate click or scroll, or drag on that app goes to the foreground directly, without a background attempt first.

With `restore_focus` (`PI_COMPUTER_USE_RESTORE_FOCUS`, default `true`), after an `act_ui` call that delivered granted foreground input and left the target frontmost, the helper's `restoreUserFocus` gives focus back to the app and the key window that were in front before; the window is named by its id, and the helper restores only while the target is still the frontmost app. When the target was already frontmost on another of its windows, that window is made key again (`target_window_restored`); the windows are compared by window id, else by the helper's window ref, so a key window that has no window id is still restored. It is skipped when the target was already frontmost on the acted window (`target_was_frontmost`) or you switched to another app (`user_switched`), and its result never changes the act outcome. `focusRestored` says the app came back; `focusWindowRestored` says whether the captured window is key again, and `focusRestoreReason` is `restored` (app and window), `app_restored` (no window could be identified before the call), or `app_restored_window_not_restored`.

Pi runs the tool calls of one assistant message concurrently. Everything from capturing your focus through a call's foreground input to its focus restore runs under one process-wide section, so concurrent `act_ui` calls take turns in the foreground and never mistake each other's activation for yours; background and accessibility-only delivery stay parallel. A call waiting for the section can be cancelled. If a call ends while the helper may still be delivering (a cancel acknowledged as `stopping` or not acknowledged, a client timeout, or the connection failing or closing, or a reply that cannot be decoded, after the request was written, reported as `execution.reason: connection_lost`), the section stays closed until the helper reports that request stopped or finished, or at most until the request's budget plus 2 s; after a release at that bound, the next call's `execution.foregroundSection.previousDeliveryUnconfirmed` names the request.

`/computer-use` shows the settings, sources, and this session's grants and denials. `/computer-use grant ask|always|off` sets the prompt mode for the session and saves it to the user file.

Foreground input goes through the system event tap, which delivers it to whatever app and window are in front at that instant. So before each foreground gesture (a click sequence, a drag, a scroll, a key or chord, a chunk of text), the helper checks the destination: the frontmost app (the system's focused application) must be the target, and the target's focused (or main) window must be the observed window: the look's own AX window while it is alive and is a window or sheet, else the window resolved from the look's window id. For a pointer gesture, the element under the point must also not belong to another process. Before the action has sent anything, the helper waits up to 400 ms for this to hold. If it does not, the helper sends nothing and refuses with `foreground_not_acquired`, carrying `inputSent: false` and `activationAttempted`. While typing, the helper rechecks at least every 100 ms, and every event requires the target to be frontmost. On a loss, it stops with `foreground_lost` (`inputSent: true`, plus `charactersSent` for text). A mouse-up or key-up is never withheld, since a withheld release would leave the button or key held; after each one the helper checks again that the target is frontmost and otherwise stops with `foreground_lost` instead of reporting the gesture delivered. When a window cannot be resolved but the app is frontmost, the input is sent and `performed.destinationWindow` is `unverified`. Neither refusal is retried in the same call. Asking the target to activate is itself a side effect, so `effectPossible` can be `true` while `inputSent` is `false`. If the call captured your focus, focus is restored as above once the target is checked again after a short wait, so a late activation does not leave it in front. The check narrows the window in which you can switch apps before input lands; it does not close it.

## Extended background delivery

`background_delivery` (`PI_COMPUTER_USE_BACKGROUND_DELIVERY`) is `standard` by default: everything above, unchanged on the wire and in results. `extended` is an opt-in. A tool call captures the mode when it starts, the same way it captures the app policy, and every background attempt it sends carries the additive field `backgroundDelivery: "extended"` (protocol 8 is unchanged). Without the field, the helper behaves as before. `/computer-use` shows the mode and whether the helper can use it.

**Capability.** `diagnostics.extendedDelivery` is `{available, osMajorVersion, measuredOSMajorVersions, missingSymbols, reason?}`, and `diagnostics.invariants` includes `extended-background-delivery`. It is available only when `SLPSPostEventRecordTo` (SkyLight), `GetProcessForPID`, and `CGEventSetWindowLocation` all resolve with `dlsym`, and the OS major version is one where the mechanism was measured (27). These are undocumented interfaces. On a helper where it is unavailable, a request for it is delivered as standard and reports `performed.extendedDelivery: "unavailable"` (or `error.extendedDelivery` on a refusal) with `extendedDeliveryReason` (`missing_symbols` or `os_not_measured`). It is never an error.

**Mechanism.** For an act that uses it, before any baseline of the settle window is taken, the helper posts to the target's pid an AppKit `applicationActivated` event addressed to the look's window and two key-window event records (`SLPSPostEventRecordTo`, addressed by the process serial number), then waits 30 ms; for pointer input it then waits up to about 200 ms more, posting nothing and never refusing, until the look's window is key, so the activation's own key-window change is not read as the act's effect. If it lands later than that (measured on a target's first activation under load), the target's focused window becoming the look's window, and the focused-element change that comes with it, still do not count as the act's effect. Every pointer event it then posts to the pid (move, down, up, drag, scroll) carries the window id in CGEvent integer field 51 and the window-local point (`CGEventSetWindowLocation`). Before any key event (`typeText`, `keypress`, web `setText`), the look's window must be the target's key window; the helper waits up to about 200 ms, posting the records once more, and otherwise refuses with `foreground_required` before any key is sent (`keyWindowAcquired: false`, `observedWindowResolved: true`). A window that cannot be resolved (neither the look's AX window nor an AX window paired with its window id) cannot be confirmed key and is refused the same way, with `observedWindowResolved: false`. Web content that advertises `AXPress` is pressed through Accessibility instead of being refused, other web pointer input is a pid attempt, and web text fields are focused through Accessibility and typed one key event per character (`performed.textEntry: "characters"`); an AX value write and a single atomic Unicode event do not reach web pages in the background.

**Scope.** It applies only to a `background` act with pid delivery, on a target that is not frontmost and whose look has a window id. The result says why it did not apply with `extendedDelivery: "not_applicable"` and `extendedDeliveryReason`: `policy_<policy>` (a granted foreground act uses HID as before, `ax_only` sends no events), `target_frontmost`, `no_window_id`, `stale_ref`, `menu_element` (the element or one of its six nearest ancestors is a pop-up button, menu button, menu, menu item, menu bar, or menu bar item, which take key status from the user's app), `secure_text` (stays as today), `web_ancestry_inconclusive`, and, for native elements that accessibility already acts on in the background, `ax_action` (AXPress), `ax_focus` (text fields), and `ax_text` (`setText`). The element must be positively identified: for a coordinate it is read from the target's own accessibility tree (the hit test of its application element, which another app's window covering the point does not change) and must lie in the observed window; for input to the focused element, the app's focused element must resolve and belong to it. That hit test follows the target's own window order, so when another window of the target lies on top at the point it answers with that window; the pointer events are addressed to the observed window and reach the observed window's element there (measured), so the helper then reads that element from the observed window's own tree by frame, with the rules of an off-Space window below (the window must pair with the look's window id), and an element of the covering window that is or opens a menu is refused as `menu_element`. Otherwise it is `element_unidentified` and standard delivery is used. A blocked app is refused before any of this, as before.

**Deactivation.** The target is told it is inactive again (`applicationDeactivated`) on every exit of the act: success, error, cancel, and deadline. Acts in flight for the same pid are counted, and the last one to end sends it. Orderly daemon shutdown (the `shutdown` command, SIGTERM, SIGINT, SIGHUP, or stdin EOF in pipe mode) sends it for every target still marked active before the process exits; from then on no act can activate a target (it is refused with `helper_shutting_down` before anything is posted). A crash or SIGKILL cannot: the target then keeps believing it is active until it is next activated or deactivated. The per-act state (window id and frame) lives in the request's context, so concurrent acts on two targets never share it.

**Answers.** `performed.extendedDelivery: "used"` and `evidence.extendedDelivery: "used"` mark an act that used it. `worked` still needs the target-specific evidence described above. An act whose effect was not observed answers `unknown`, never `foreground_required` or `didnt` (with `evidence.observableChange: false`), because the input reached the app: in the measurements, delivered acts had their effect although the settle window saw no change. The same holds for an act that ends after the activation where it would otherwise have been refused (a web text field that does not take accessibility focus, for one): it answers `unknown` with `evidence.extendedDeliveryEnding: {code, message}`, and an `actBatch` stops at it. Only the key-window refusals, raised before any key, stay refusals; in an `actBatch` such a step is `unknown` and its error carries `extendedDelivery`. Every error of an act that asked for it carries `extendedDelivery` and `extendedDeliveryReason`. On the TypeScript side, a refusal whose evidence or error says `extendedDelivery: "used"` is never read as proof of no effect: in a single act and in an `actBatch` step it is reported as `unknown` (no refusal, no `foreground_required` result), it is neither retried in the foreground in the same call nor turned into a grant prompt, and a `didnt` answer from such an act is never turned into a refusal. An `act_ui` call stops at an act that ended this way: later actions are not sent, and the text says so. The `act_ui` text says when extended delivery was used, and `details.config.background_delivery` appears only under `extended`.

**Risks.** The target believes it is active for about half a second per act, so an app that reacts to activation may open panels or activate itself. The key-window records inject one extra mouse-down that the app sees. A hard crash of the helper leaves the target believing it is active. It was measured on one OS version (macOS 27.2.1, arm64) against the fixture apps and Chromium; other apps may react differently.

## Windows on a hidden Space

A window on a Space that no display is showing (another desktop Space of any display) is off-Space. AppKit leaves it out of `kAXWindows`, so the helper used to list, observe, and act on none of them. It now handles them without switching a Space, changing the frontmost app, or raising the window, within the rules below. The checks for it are the off-Space harness (`e2e/safety/offspace.ts`) and `tests/off-space.test.ts`.

**Listing.** For each app, `find_roots` lists a window `kAXWindows` omitted when it is a layer-0 window of at least 100x80 points with alpha above 0, of an app that is not hidden, and every Space it belongs to (`CGSCopySpacesForWindows`) is a desktop Space that no display currently shows (`CGSCopyManagedDisplaySpaces`). Windows of hidden apps, a resolved window that reports itself minimized, windows on a full-screen Space, windows on every Space (they are on a shown one), and ordered-out windows (on no Space) are not listed. Such a root has `off_space: true`, `isOnscreen: false`, and `off_space_access`: `readable` (the helper found its accessibility element without activating anything), `needs_discovery` (the app has not exposed it), or `unchecked` (a listing across all apps does not scan for it; filter by app or pid). A listing never activates anything. The helper reads the app to resolve the element (its earlier resolution, the app's focused and main windows, and, for a listing of one app, a remote-token scan) only when the request's app blocklist allows the app; `listRoots` carries the blocklist for this alone and is still not filtered. A blocked app's off-Space window is listed from the window server only and flagged `blocked`.

**Observation.** `observe_ui` resolves an off-Space window after the app policy and before any capture. A window that resolves without activation is observed in either mode. One that does not is refused in `standard` with `off_space_window_unresolved`, whose message says that the app has not exposed the window (it has not been shown on a visible Space since it opened), that the user can show it once, and that `background_delivery: "extended"` would let the helper expose it. Nothing is activated or captured. Under `extended` (the look carries `backgroundDelivery: "extended"`) with the capability available and the app not frontmost, the helper uses one discovery activation: the activation event and key-window records an extended act sends, a re-resolution for about 200 ms (focused and main windows, then the token scan), and the deactivation on every exit path and at orderly shutdown. Measured: activation alone, or the key-window records alone, do not expose the window; after one discovery it stays resolvable. If it still does not resolve, or discovery is unavailable or the app is frontmost, the look is refused with the same code and a message that says which. The capture is the usual ScreenCaptureKit capture and is current; frames are global as if the window were on screen. `details.off_space` is `{discovery_activation, resolved_by, spaces_unchanged?}` and the text says that the window was read without switching Spaces and whether discovery was used.

**Acting.** Accessibility actions (press, `set_text`, focus) work in both modes, as on any background window. Pointer and key input follow the extended-delivery rules above: under `standard`, pid pointer input carries no window and has no effect on an off-Space window, so a click without an accessibility action is refused as `foreground_required` as today. Under `extended`, the element at a coordinate must still be identified for the exclusions (menus, secure text fields). The application's hit test cannot see an off-Space window, so only when it gives no answer, the helper reads the element from the look window's own tree by frame (the same reading applies on a shown Space when another window of the target lies on top at the point): it descends through the one child whose frame contains the point, skipping children that report `AXHidden`. Accessibility order is not z-order and frames ignore clipping and drawn overlays, so when two children at one level contain the point, at the depth bound (32), or when nothing below the window contains it, the element is unidentified and standard delivery applies (`element_unidentified`). An act on an off-Space window reports `performed.offSpace: true`, and the `act_ui` text says the input was sent in the background without switching Spaces. Acts never use the discovery activation.

**Foreground.** Foreground input to an off-Space window would bring it to the front and switch the user's Space, so the helper refuses a `policy: "foreground"` act on it, and `focusWindow`, with `off_space_foreground` (`effectPossible: false`, `inputSent: false`, `activationAttempted: false`) before anything is activated or sent. The TypeScript side does not send one: a foreground grant does not move an act on an off-Space target to the foreground, a background refusal is not escalated, no grant prompt is shown, and the refusal hint says why.

**Capability.** `diagnostics.offSpace` is `{available, discoveryAvailable, osMajorVersion, measuredOSMajorVersions, missingSymbols, tokenIdLimit, tokenScanBudgetMs, reason?, discoveryReason?}`. It is available only when `_AXUIElementGetWindow`, `_AXUIElementCreateWithRemoteToken`, `CGSMainConnectionID`, `CGSCopyManagedDisplaySpaces`, and `CGSCopySpacesForWindows` all resolve with `dlsym` and the OS major version is 27; discovery also needs extended delivery's capability. Otherwise no window is treated as off-Space and listing, observation, and acts behave exactly as before. The token scan builds a 20-byte remote token (pid, 0, the constant 0x636f636f, a 64-bit element id) for element ids 0 to 4095 within 500 ms, with a 50 ms messaging timeout per element, and keeps a match only when its owner pid, its role (`AXWindow`), and its window id (`_AXUIElementGetWindow`) all match; a mismatch is never used. A window whose element id lies beyond the range, or that a slow app does not answer within the budget, is not found: its observation then needs discovery or is refused. Resolved elements are cached per window id and verified again on each use.

**Risks.** During discovery the target believes it is active for at most about 0.75 s (30 ms, up to 200 ms of re-resolution, and at most one 500 ms token scan; usually far less), so an app that reacts to activation may open panels or activate itself, which would switch the Space. The token layout and the Space calls are reverse-engineered, undocumented interfaces, measured on one OS version (macOS 27.2.1, arm64) with the fixture app only. Not measured: a target in its own full-screen Space (not listed), minimized windows and hidden apps (not listed), second windows of one app, real apps, web content, a target on a hidden Space of another display than the one the check used, and foreground (HID) delivery.

## Action results

`act_ui` validates every action before it sends any. An invalid action (a stale ref, coordinates outside the image, a scroll without target, keyboard x/y, headless keyboard input without ref, and so on) rejects the call before delivery, and the state_id stays usable. In a multi-action call the error is prefixed `act_ui action N (<action>):` and ends with `Nothing was sent.`

On a native text field or area, `set_text` focuses the field, selects its text, and replaces the selection through Accessibility, the route typing takes, so the app's text delegate and bindings see the change (`performed.textCommit: selected_text`); it is `worked` when the value reads back. When the field offers no such route, the helper writes the value only (`textCommit: value`, with `textCommitUnavailable` naming why), and the read-back, matching or not (`evidence.valueMatches`), is `unknown` with `evidence.valueWriteOnly: true` (a control may normalize the text; a write the accessibility API rejects falls back as before): the view shows the text, but the app (a SwiftUI binding, for one) may not have seen it, and the next observation does not upgrade it to `worked`.

Typed text does not depend on the user's keyboard input source, and the helper never changes that source. A key event created from a key code alone takes its characters from the current source's layout (measured with Korean 2-Set: `typeText` of `c1:abde` into a background AppKit field arrived as `ㅊ1:ㅁㅠㅇㄷ` and was answered `worked`). So: (1) `type_text` into a native (non-web) text field or area replaces the field's selection, the caret, through Accessibility (`performed.textEntry: selected_text`, `delivery: ax`), the route `set_text` takes, with no key event, in every delivery mode; (2) every other typed character (web content, fields without that route, `keypress` of a printable key) is sent as key events that state the character itself (`keyboardSetUnicodeString` on every event, the key code only for apps that read it); Control and Option chords keep the system's translation; (3) granted foreground (HID) key text goes through the frontmost app's input method, which composes keys whatever characters they state, so while the current source is an input method or mode (Korean, Japanese, Chinese) such text is refused before any key with `input_source_composes` (native fields are not affected, they take the Accessibility route). `type_text` answers `worked` only when the field's value reads back exactly as typing the text into its selection should have made it (`evidence.valueMatches: true`); a changed value that differs is `unknown` with `valueMatches: false`, an unchanged one `didnt`, and a value that cannot be read is never `worked` (`valueReadable: false`). Secure fields are refused as before. Focusing a text field through Accessibility makes AppKit select all of its text, so a key or text after the focus had moved elsewhere would have replaced the whole value (measured: a second `backspace` cleared a 39-character field); when focusing selects the whole value, the helper puts the caret back where its last act in that field left it, else at the end. Background `pid` scroll wheel events are addressed to the observed window (as extended delivery addresses pointer events); without that they reached the app with no window and had no effect. `diagnostics.inputSource` reports the current source (`id`, `type`, `asciiCapable`, `composes`).

When an action fails during delivery after earlier actions ran, the result has `details.status: "partial"` and a fresh successor state. `execution.steps` lists the delivered actions and the failed one (with request ids), `execution.stoppedAt` is the failed action's index, and `execution.error` carries the helper's code, message, and `effectPossible` (and, for a foreground destination refusal, `inputSent`, `activationAttempted`, and `charactersSent`). Focus is restored as after a complete call. A failure of the first action still rejects the call, with two exceptions. A first-action `foreground_not_acquired` returns `details.status: "foreground_not_acquired"`, with `details.error.inputSent: false`, no successor state, and text that says no input was sent because the target did not come to the front. A first-action `foreground_lost` returns a partial result with `stoppedAt: 0`. A cancellation or ownership refusal after earlier actions ran reports them in `execution.steps` with the transaction index in `stoppedAt`; focus is not restored while the helper may still be sending. Any result after which the UI may have changed (a partial call, a cancellation after delivery, or a refusal that followed delivered actions or may itself have taken effect) invalidates the base state_id.

Browser (CDP) pages follow the same rules. Before anything is sent, each action is checked against the state: refs must be actionable controls, ref clicks use the left button, `move_mouse` takes x/y only, `scroll` takes a ref or no target (the page) but no x/y, `keypress` keys must be DOM key values (one character, a name such as `Enter` or `ArrowRight`, or a modifier, with at least one non-modifier); on macOS, Cmd editing shortcuts (select all, copy, cut, paste, undo, redo) do not run on browser pages, so use `set_text` to replace a field's text, and points must lie inside the viewport recorded with the state (a state without a recorded viewport skips that check). A read-only CDP check then confirms that the page still exists and every targeted node still resolves and is still in the page; a ref whose element is removed during the call fails that step (`element_detached`). A browser result carries `execution.steps` with `strategy: "cdp_act"`; a sent step's outcome is `unknown`, and a failed step's `error.effectPossible` is false only when that action sent no input. A failed `expect` returns the successor with `execution.verification.status: "failed"`. When the page cannot be observed afterward, the result is `target_closed` or `post_action_observation_failed` without a successor. A ref `click` or `press` focuses a focusable target before clicking, as a real click does, so keyboard input without ref then goes there. `keypress` with a ref focuses that element first, and keyboard input without ref is allowed on browser pages in headless mode.
