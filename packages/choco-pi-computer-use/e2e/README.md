# Computer-use E2E harness

Run from the dev worktree only. `node --experimental-strip-types packages/choco-pi-computer-use/e2e/run.ts --tier a --dry-run --preflight-only --baseline <path>` prints the exact isolated Pi commands, symlink targets, env and artifact paths without spawning Pi. `--pi /opt/homebrew/bin/pi` must fail with `PI_VERSION_MISMATCH` (exit 2). A live run requires `--baseline <path>` with root-gate evidence, the fake daemon at `CU/tests/helpers/fake-helper-daemon.ts`, and authorization to spawn Pi; if that file is missing, the tier-A launcher refuses with `FAKE_DAEMON_MISSING`. No installer, signing, or permission request is made here.

`--models <ids>` and `--scenarios <S-ids>` take comma-separated lists and default to all. A model filter entry may name the configured id or its `--substitute` target; unknown or duplicate ids exit 2 with `ARGUMENT`. A scenario filter must include `S1`, because only S1's isolation checks decide whether later scenarios run; scenarios always run in S1–S7 order. Preflight still checks both configured models. `summary.json` records the selected `models` and `filters: {models, scenarios}` (`null` when unfiltered).

The baseline's top-level `gates` object must name `lint`, `fmt:check`, `typecheck`, and `test`. A non-zero status requires an explicit, repeatable `--waive-gate <gate>=<reason>` for that exact gate; passing gates cannot be waived. Each accepted waiver is printed and recorded with the original red status in `<scratch>/summary.json`. Evidence reports must reproduce these entries in a **Gate waivers** table, even if the table says “None”. See `docs/computer-use-e2e.md` for the format. A waiver records an out-of-scope red gate; it does not claim the gate passed.

Tier A daemon CLI contract: `node --experimental-strip-types tests/helpers/fake-helper-daemon.ts --socket <scratch>/a/bridge.sock --script S1..S7 --log <scratch>/a/<model>/<scenario>.requests.jsonl --executable-path <scratch>/a/pi-computer-use.app/Contents/MacOS/bridge`. It serves newline-delimited JSON request/response envelopes, protocol 8 diagnostics and granted permissions, and logs each request with `cmd`, `id`, `session`, `policy`, and `foregroundGrant`. It logs `act`/`actBatch` rows when it answers them, adding `response` (the reply without `id`). It logs `cancel` rows as `target` (the act's `requestId`) plus `ack:{acknowledged,state,stoppedAt,effectPossible}`. It must simulate `foreground_required`, `didnt`, cancellation and ownership in their respective scenarios. In S4 (`--deadline-overrun-ms 250`) it holds the typeText to its deadline and 250 ms longer in a step no cancel interrupts, so the TS transport timeout (equal to the act's `budgetMs`) fires first and the transport's own `cancel` stops it at the next checkpoint; the harness never signals Pi. The harness sends a second-session `act` after the first primary action in S7 and a mutation `look` request with `fixtureMutation:"bump_root_generation"` in S5. The fake reports the supplied executable path in diagnostics for S1 isolation checks. The harness spawns it with `stdio: ["ignore", "pipe", "pipe"]`, drains both streams to `<scenario>.daemon.log`, and stops it with SIGTERM, then SIGKILL after 2 s, waiting at most 5 s. `process.ts` holds the bounded wait helpers and `launch.ts` holds the Pi runner. `process.test.ts` and `launch.test.ts` test them with dummy children and never spawn Pi.

Tier B (`--tier b --helper-app <dev app> --helper-socket <dev daemon socket>`) needs explicit authorization for the desktop, an independently installed and signed dev helper, and a dev daemon that is already running with TCC granted. The harness never installs, signs, or launches a helper and refuses the main helper app or socket. Pi connects to `<scratch>/b/bridge.sock`, where `proxy.ts` forwards bytes unchanged to the dev daemon and writes `<scenario>.requests.jsonl` in the fake daemon's row shape (`origin`, `seq`, `at`, `respondedAt`, `response`, `ack`). In S4, the target is launched with `CU_FIXTURE_WEB=1`, Pi runs with extended background delivery, and the model types 400 characters into the web window's input, which arrives as one key event per character; the proxy cancels that typeText if it is still in flight after 2 s (`origin:"harness"`, carrying the act's `session`, since protocol 8 refuses a cancel from another session), because the real helper finishes before the TS transport timeout. `fixture/main.swift`, `fixture/fixture_app.swift`, and `fixture/fixture_views.swift` (one binary, built by `fixture/build.ts` into `<scratch>/b/fixture/<hash>/`; no binary is committed) provides the disposable target (`com.choco-pi.FocusFixture`: Field, Increment, and a Custom View without AXPress) and holder (`com.choco-pi.FocusHolder`) apps. `desktop.ts` launches the holder, then the target without activation, proves that the holder is frontmost, performs the S5 `.cu-resize`, and quits both apps. Each app logs to `<scenario>.attempt-<n>.<session id>.fixture/{target,holder}.jsonl`, a fresh directory per attempt. `tier-b.ts` scores S1–S6 from those logs and the proxy log; `tier-b.test.ts` covers it with synthetic logs. Rules are in `docs/computer-use-e2e.md` under “Tier B”. Never run tier B against TextEdit, Notes, or user documents. The harness does not call `registerPermissions` or `openPermissionPane`.

Evidence is written under `${PI_SCRATCH_DIR}e2e/{sessions,a/<model>,b/<model>}` (the host's scratch directory; `/tmp/choco-pi/<PI_SESSION_ID>/e2e/` when `PI_SCRATCH_DIR` is unset). A run report must name date, revision, Pi/Node versions, scratch and isolation proof, scenario PASS/FAIL/INCONCLUSIVE/BLOCKED with session/event/request/fixture log paths, and failures/deviations. These are machine-checked verdicts, not summaries of model prose. Never publish or attach full-screen captures or credentials. Scoring rules (rejected-before-dispatch calls, per-step delivery, once-per-scenario headless check, `INCONCLUSIVE(no_dispatch)`, isolation-only blocking) are in `docs/computer-use-e2e.md`; `assertions.test.ts` replays recorded S1, S3 and S5 evidence in `fixtures/<scenario>/<model>/`, where events and sessions are stripped of streaming deltas, thinking blocks and signatures. It also scores synthetic S4 and S6 evidence in the fake daemon's log shape. The S5/S7 intervention reply is saved as `<scenario>.intervention.json`.

## Safety harness (`safety/`)

A deterministic, model-free check of where computer-use input lands and whether focus comes back. It drives the real helper against the disposable fixture apps and judges each scenario only from the fixtures' own logs; the helper's `worked`/`didnt`/`unknown` answer is kept in `summary.json` as a prediction, never as the verdict. Scenarios assert the safe behavior, so on a helper with the targeted defect they FAIL; once fixed they are its pass criterion.

```sh
node packages/choco-pi-computer-use/e2e/safety/run.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> [--scenarios <id,id>]
```

Like tier B it needs explicit desktop authorization and an already running, signed, TCC-granted dev helper; it never installs, signs, launches, or shuts down a helper, and refuses `~/Applications/pi-computer-use.app`, `/Applications/pi-computer-use.app`, and `~/Library/Caches/pi-computer-use/bridge.sock` (`HELPER_IS_MAIN`, exit 2). Before each scenario it checks daemon `diagnostics` (executable realpath under `--helper-app`, Accessibility and Screen Recording granted; the protocol version is recorded, not required) and claims/releases a probe session, waiting up to 40 s for another owner; otherwise the scenario is `BLOCKED(<reason>)`. The final line counts PASS, FAIL, BLOCKED and INCONCLUSIVE scenarios separately (`safety summary <path> (complete: 25 passed, 0 failed, 0 blocked, 3 inconclusive of 28)`), and the exit code is 0 only when the run completed and every scenario PASSed: an INCONCLUSIVE scenario proved nothing, so it fails the run like FAIL and BLOCKED.

Two layers drive the helper. Raw-wire scenarios (`safety/wire.ts`) send `claim`, `listWindows`, `look`, `act` (with `policy`/`foregroundGrant`), `cancel`, `getFrontmost`, `restoreUserFocus`, and `release` themselves. TS scenarios import the package's `executeFind`/`executeObserve`/`executeAct` (`safety/ts-layer.ts`) with `PI_CU_SOCKET_PATH`, `PI_COMPUTER_USE_HELPER_APP_PATH`, and `PI_COMPUTER_USE_FOREGROUND_GRANT=com.choco-pi.FocusFixture` set before import and a scratch `PI_CODING_AGENT_DIR`. Their socket is `<out>/ts.sock`, an in-process guard proxy (`safety/guard-proxy.ts`) that logs every request and answers `shutdown`, `registerPermissions`, and `openPermissionPane` itself (`harness_forbidden`); a scenario whose TS layer tried one is `BLOCKED(ts_requested_forbidden: …)`.

Each scenario gets a fresh `<out>/<id>/fixture/` log directory and fixture instances (`holder.jsonl`, `target.jsonl`, or `a`/`b`/`other`), a bounded timeout, and cleanup that quits every instance (`.cu-quit`, SIGTERM, SIGKILL) even on failure. At the end the harness kills any leftover process from its fixture build, runs `lsregister -u`, and re-activates the app that was frontmost before the run if it still runs. `<out>/summary.json` lists per scenario the verdict, first failed assertion, helper answers (observation replies reduced to ok/error/look id), notes, and the request-log and fixture-log paths; `<out>/<id>/requests.jsonl` uses the proxy row shape. No screenshot or outline is written. Scoring lives in `safety/score.ts` as pure functions; `node --test packages/choco-pi-computer-use/e2e/safety/score.test.ts` feeds synthetic logs that pass and fail each rule.

Fixture options for the harness are opt-in environment variables, so tier B is unchanged: `CU_FIXTURE_INSTANCE` (row field `instance` and trigger-file suffix), `CU_FIXTURE_WINDOWS=2`, `CU_FIXTURE_SAME_TITLE=1`, `CU_FIXTURE_KEY_WINDOW=<n>`, `CU_FIXTURE_STICKY=1` (holder re-activates itself as soon as it resigns, emulating a denied or late activation), `CU_FIXTURE_COVER=x,y,w,h` or a `.cu-cover-<instance>` file (holder window covers that top-left screen rect), `CU_FIXTURE_NOISE=1` (a hue-cycling box away from the controls), `CU_FIXTURE_DEAD_VIEW=1`, `CU_FIXTURE_WEB=1` (a WKWebView window whose input logs `webValue` through a script message handler), `CU_FIXTURE_ACTIVATE=1`, `CU_FIXTURE_OFFSET=dx,dy`, a `.cu-activate-<instance>` trigger file, and a `.cu-yield-<instance>` trigger file (body `<pid> <instance>`: this active instance yields activation to that pid, activates it from its own context, and writes that instance's `.cu-activate-<instance>`), `CU_FIXTURE_UNPAIRED_WINDOW=1` (a small extra target window whose AX element reports role group, title `AX Alias`, and a frame 6000 pt away, so it pairs with no window id; its window number is logged as `unpairedWindow`), and `CU_FIXTURE_SPAWN_CHAIN=<n>` (the target runs `<n>` nested `/bin/sh` levels from `chain.sh` in its log directory; the leaf writes `chain-leaf.pid` and sleeps 120 s). `CU_FIXTURE_MATRIX_OVERLAP=1` (matrix mode: the SwiftUI window at x 100 instead of 1220, over the AppKit window's pop-up button and drag view). Always on and additive: every window is placed with `setFrame` after it is made, since `NSWindow.init(contentRect:)` can move a new window depending on the screen configuration (measured on macOS 27 with the keyboard focus on another display: the matrix windows moved from the top to the bottom of the primary display, and windows at x 1220 to x 100), and `launched` logs each window's `requestedFrame` next to its `frame` and the `screens`; `run.ts` scenarios are `BLOCKED(layout: …)` when a window is not where it asked to be or not wholly on the primary display, and record the layout in `notes.layout` (global top-left points). The layout is the one for the primary display, whose top-left is (0, 0), independent of which display has keyboard focus and of the Spaces shown. The holder logs `mouseDown`, and `windowKey`/`windowResignKey`/`keyDown`/`appActive` rows name their window (`window`, `windowNumber`, `title`).

### Delivery matrix (`safety/matrix.ts`)

A measurement mode next to the scenarios (which it leaves unchanged): what background-only delivery achieves per UI surface and action, with no verdicts.

```sh
node packages/choco-pi-computer-use/e2e/safety/matrix.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> [--reps 5] [--fg-reps 2] [--looks 20] [--surfaces appkit-main,appkit,swiftui,webkit,chromium] [--cells <substring,...>] [--no-chromium] [--skip-latency] [--settle-ms 800] [--background-delivery standard|extended] [--after-check]
```

It has the same helper checks and refusals as `run.ts` (`HELPER_IS_MAIN`, diagnostics, probe claim) and runs on the raw wire. Each cell (surface × action: `click_ref`, `click_xy`, `set_text`, `type_text`, `key` `x`, `chord` cmd+a, `scroll_ref`, `scroll_xy`, `drag`) runs `--reps` times with `policy:"background"` and no grant, then `--fg-reps` times with a foreground grant (HID delivery, with `restoreUserFocus` after each one) as a reference. Every fixture cell gets a fresh target and holder per phase. Before each repetition the holder must be frontmost. The fixture is then reset (`.cu-reset-target`), and a fresh `look` (with an image, which is not stored) supplies the ref or the coordinates. A repetition whose precondition fails is recorded as skipped and not counted. Each repetition records the helper's answer (outcome, or the refusal code with its evidence), whether the fixture logged the intended effect and whether that happened more than once, every holder disturbance (`appInactive`, `windowResignKey`, `keyDown`, `mouseDown`, another app frontmost), whether the target process saw the input at all, and the act's round-trip time. Each surface's window is then looked at `--looks` times in three configurations (image with `readText` never, image with `readText` always, no image), recording the helper's `timings`, the outline node count, the reply size, and wall time. Output is `<out>/matrix.json` (all repetitions and samples, act replies reduced to outcome/performed/evidence/error) and `<out>/matrix.md` (tables). Scoring is pure in `safety/matrix-score.ts`.

Surfaces come from `CU_FIXTURE_MATRIX=1`, which only the matrix sets: the main target window (`appkit-main`), a `CU Matrix AppKit` window (scroll view, drag view, pop-up button that closes itself after 400 ms, checkbox), a `CU Matrix SwiftUI` window (`NSHostingView`: Button, TextField, Toggle, `onTapGesture` view without a press action), and the web window, which loads `CU_FIXTURE_WEB_PAGE` (`safety/matrix-page.ts`: input, button, a role-less click `<div>`, a scroll region, a drag region). In this mode the target also logs `targetKeyDown`/`targetMouseDown`/`targetScrollWheel`, `responder`, `editorSelection`, and `resetDone`. If `/Applications` has Google Chrome (or Chromium, or Chrome Beta), `chromium` runs the same page from a `127.0.0.1` server on a random port; the page reports each event with `fetch`, and the server log is that surface's fixture record. The browser binary is spawned directly with a fresh `--user-data-dir` under `<out>`, `--no-first-run --no-default-browser-check --use-mock-keychain`, and other flags that disable sync and background networking. After each phase it is stopped together with the processes it owns: the spawned pid and its descendants, recorded every 2 s while it lives (with their start times, so a reused pid is not taken), and a non-descendant only when its executable lies inside the launched app bundle and its command line carries this run's `--user-data-dir=<dir>` (a crash handler: a `--database=` or `--annotation=` argument naming that directory). Any other process in that bundle or naming the directory is a leftover: waited for up to 10 s, then reported (`chromiumStops[].leftovers`, a defect, and a `chromium leftover` line) and never signalled. `safety/chromium.test.ts` tests the rule on synthetic process tables and `safety/chromium-ownership.test.ts` against a fake browser bundle and impostor processes. No other browser process or profile is touched.

`--background-delivery extended` adds the product wire field `backgroundDelivery: "extended"` to every background repetition (the foreground reference is unchanged). For each fixture repetition the matrix records the target's own focus rows in the act window (`notes.targetFocusRows`, `targetMouseWindows`), whether it still believes it is active (`targetBelievesActive`), and the extended-delivery status the helper reported (`notes.extendedDelivery`). With `extended` or `--after-check`, `matrix.md` adds a "Target after-state" table per cell (extended used, other statuses, target activated during the act, target left active; `n/o` for Chromium, whose page has no activation log). `--after-check` also runs, 1 s after each cell's background repetitions, a check of the idle target, a granted click on the holder, and one granted act on the target (`afterChecks` in `matrix.json`).

### Display check (`safety/displays.ts`)

A model-free check that observation, coordinate acts and the agent cursor overlay are right on displays other than the primary one, including displays at negative global coordinates.

```sh
node packages/choco-pi-computer-use/e2e/safety/displays.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> --displays <id,id> [--min-displays 2] [--overlay-only]
```

It has the same helper checks and refusals as `run.ts` (`HELPER_IS_MAIN`, diagnostics, probe claim), never launches the holder, never activates anything, and never re-activates an app at the end. It first launches a windowless fixture (`CU_FIXTURE_SCREENS_ONLY=1`) that logs every screen (id, CoreGraphics bounds, its Cocoa frame converted to top-left points, backing scale, whether it is `NSScreen.main`). Without `--displays` it stops there and lists the displays (`LIST`, exit 1): `NSScreen.main` in a background app is not reliably the screen the user works on, so the operator names the displays to test and leaves out the one in use. On each named display it opens one matrix fixture (`CU_FIXTURE_MATRIX=1`, `CU_FIXTURE_ORIGIN=<display top-left>`); a display whose fixture windows are not on the active Space or not inside it is unusable, and with fewer than `--min-displays` usable displays the run is `SKIP(<reason>)` (exit 0). If the frontmost app changes at any point (`lsappinfo front`), the run stops at once (`ABORTED(frontmost app changed …)`).

Per usable display: the look's window frame lies on the display and matches the fixture's own frame; `scaleFactor` equals the display's backing scale and the image is `frame.w × scale` wide; the Custom View, Field, scroll view and drag view frames (outline rects mapped to global points) match the fixture's and lie on the display. Acts: an extended (`backgroundDelivery: "extended"`) coordinate click on the Custom View, scroll on the scroll view and drag across the drag view, each judged by the fixture's row (`customHit`, `scrollPosition`, `dragUp` A→B) and by the event's global location (`at`, within 2 pt of the intended point); a standard AX press on Increment and standard typing into Field, judged by `increment` and by a `fieldValue` of the typed length (the characters follow the active keyboard input source; `valueMatches` records whether they equal the typed text). After each coordinate act it checks the overlay: the fixture reads the window server's entries for the helper's pid (`.cu-owner-windows-<instance>`), and an on-screen helper window must contain the acted point and lie inside the display containing it (a per-cursor window, or the older full-display overlay), with no helper window straddling displays or covering another whole display (cursor windows of earlier acts on other displays may still be fading). When the helper answers `agentCursorState` it also requires that the helper reports the same display, that the window server's bounds of its cursor window lie inside the display, that the drawn target is the acted point minus the display's top-left, and that the pointer pixels captured from the overlay window alone (`capture: true`) lie within 4 pt of that local point and span at most 40 pt, and, on a helper that reports it, that the pointer's hot spot located in those pixels is within 1.5 pt of the acted point (`drawn_tip`). The drag's cursor check is at its drop point (the cursor follows the drag's path). A window the system moved off its display at creation is put back with `setWindowFrame` at the offsets the first display's windows have, then read again. On a helper without the command these checks are `null` (not run) and only the window-server check applies. With two or more displays a follow check clicks display 1, 2, …, 1 in a row and checks the overlay after each. `--overlay-only` does only the observation and the click per display. Output: `<out>/summary.json` (screens, per-display checks with details, follow checks, front before and after), `<out>/requests.jsonl`, and the fixture logs under `<out>/fixture/`. Scoring is pure in `safety/displays-score.ts`, tested by `safety/displays-score.test.ts`.

Display fixture options: `CU_FIXTURE_ORIGIN=x,y` (global top-left points) translates every window by (x, y), so the default layout, which is laid out for the primary display with its top-left at (0, 0), lands on the display whose top-left is (x, y); it composes with `CU_FIXTURE_OFFSET`. With it the target also logs `screens` and `layout` (windows in global top-left points with `onActiveSpace` and screen id, and the controls' global frames), adds a global `at` point to `customHit`, `dragDown`, `dragUp`, `targetMouseDown` and `targetScrollWheel`, re-logs `layout` on `.cu-layout-<instance>`, orders the window named in `.cu-front-<instance>` (`main`, `appkit`, `swiftui`) to the front without activating the app (an `orderedFront` row; the check lifts the AppKit matrix window over the overlapping SwiftUI one before its scroll and drag), and answers `.cu-owner-windows-<instance>` (body `<pid> <seq>`) with an `ownerWindows` row: number, bounds, layer, on-screen and alpha of that pid's windows, never their names. `CU_FIXTURE_SCREENS_ONLY=1` logs `screens` and `launched` and exits without a window.

### Cursor check (`safety/cursors.ts`)

A model-free check of the agent cursors under concurrency: one cursor per acting session, each at its own act's point, on the right display, gone when it should be; and that background acts never move the real pointer.

```sh
node packages/choco-pi-computer-use/e2e/safety/cursors.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> --displays <id,id> [--clients 2] [--reps 1] [--kinds click,click_ref,scroll,drag,move,press_ax,scroll_std] [--off-space]
```

Same helper checks and refusals as `displays.ts`; no holder, no grant, nothing activated: every fixture is opened with `open -n -g`, and the run aborts if the frontmost app or any display's Spaces (read by the observer fixture's `.cu-spaces-obs`) change. It launches an observer fixture (`CU_FIXTURE_POINTER_SAMPLER=1`, logging the real pointer every 5 ms) and `--clients` target fixtures (`CU_FIXTURE_PARALLEL=1 CU_FIXTURE_INPUT_LOG=1`), spread over the given displays in four slots per display, each judged by its actual frame (re-read with `.cu-layout-<label>`; a window the system moved off its display is put back with `setWindowFrame`), and connects one wire per target with its own session id. Each burst sends one act per session at once (extended coordinate click, extended click by ref, extended scroll, extended drag whose target point is deliberately not its path start, extended `moveMouse`, standard AX press by ref, standard scroll), with sub-point offsets that differ per session and repetition. While they run it samples `agentCursorState` every 20 ms; once they settle it captures every cursor window's pixels (`capture: true`). Per burst: one cursor per session present at once (`cursors_concurrent`, `max_simultaneous` over the samples); per session its target equals that session's point, a drag's drawn path equals its path, the drawn tip and the tip located in pixels are within 1.5 pt of the event location the target logged (`customHit`, `targetScrollWheel`, `dragUp`, `targetPointer` moves; the element centre for an AX press), the cursor is on the display containing the point with its window-server bounds inside it, and the window below it is its own target window; and no settled cursor is ever at another session's point (`never_at_other_session`). Then the lifecycle: a released session's cursor is gone within 600 ms and the others stay; a target that quits (SIGTERM) has its cursor gone within 1 s and no cursor is created for its window afterwards; after a fresh act the remaining cursors fade after their own 8 s idle period (not before 7 s, by 9.25 s); no helper window is on screen then; after one more burst every target quits and no helper window is on screen within 1 s. With `--off-space` a further fixture is clicked, moved to a hidden desktop Space (`.cu-space-off`), and clicked again: its cursor is removed and the off-Space act draws none. Finally the real pointer must never have been at an acted point during the run (`real_pointer_untouched`, with the count of pointer changes; changes elsewhere are the user's). Latencies (helper clock): `eventToDrawnMs` (the act asked to the cursor being drawn), `eventToArrivalMs` (to the tip resting on the point), and `clientSendToRestMs` (client side, sending the act to the first sample with that act's cursor at rest on its point). On a helper with the single legacy overlay the same checks run and fail where it has one cursor for everyone. Output: `<out>/summary.json` (placement, per-burst details, checks, latency, final cursor history), `<out>/requests.jsonl`, fixture logs. Scoring is pure in `safety/cursors-score.ts`, tested by `safety/cursors-score.test.ts`.

### Pointer restore (`safety/pointer-restore.ts`)

Takes keyboard focus: run it only when nobody is typing. A holder fixture activates itself and samples the real pointer; granted foreground (HID) click, drag and scroll on the holder's own window must move the pointer to the acted point and leave it back within 1 pt of where it started (`performed.pointerRestore`); a click during which the holder warps the pointer on its mouse-up (`.cu-warp-on-up-holder`, standing in for the user moving it) must leave it where the user put it (`reason: user_moved`); the foreground click draws an agent cursor. Before the holder quits the helper gives focus back to the app that was frontmost (`restoreUserFocus`).

```sh
node packages/choco-pi-computer-use/e2e/safety/pointer-restore.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir>
```

Fixture options for these checks (off by default): `CU_FIXTURE_INPUT_LOG=1` logs every pointer event the target receives (`targetMouseDown`, `targetScrollWheel`, `targetPointer` for moves, drags and button-up, with global `at`) and reports the scroll and drag views and Increment in `layout`; `CU_FIXTURE_POINTER_SAMPLER=1` logs `pointer` rows and arms `.cu-warp-on-up-<instance>`. `parallel.ts --cursor-overlay` runs the parallel check with the overlay on.

### Off-Space check (`safety/offspace.ts`)

A model-free check that windows on a Space no display is showing are listed, observed, and operated without any Space or focus side effect, through the product's TypeScript layer (`executeFind`/`executeObserve`/`executeAct` behind the guard proxy, `<out>/ts.sock`, logged to `<out>/ts-requests.jsonl`) and the raw wire (`<out>/requests.jsonl`).

```sh
node packages/choco-pi-computer-use/e2e/safety/offspace.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> --display <id>
```

It has the same helper checks and refusals as `run.ts` (`HELPER_IS_MAIN`, diagnostics, probe claim), never launches the holder, and never activates anything itself. Without `--display` it lists the displays (`LIST`, exit 1); name a display that shows a desktop Space and has another desktop Space. Each phase writes the user config file in `<out>/agent` (`background_delivery`, `blocked_apps`, `foreground_grant`); no grant comes from the environment. Fixtures open with `CU_FIXTURE_ORIGIN` on that display. Before and after every step the fixture logs `spaces`, and every step must keep its window off-Space (every Space it belongs to is a desktop Space and none is a display's current one), every display on the Space it showed at the start, the frontmost pid (`lsappinfo front`) unchanged, and no fixture `frontmost` row (any app activation). A Space or frontmost change stops the run at once (`ABORTED`). Typed text is digits (`24680`, `13579`), so the result does not depend on the keyboard input source.

| scenario     | SAFE when                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `seen`       | `standard`: a target shown on its display, listed there, then moved off-Space (`.cu-space-<instance>`) is listed with `off_space: true`, `isOnscreen: false`, `off_space_access: "readable"`, observed with `off_space.discovery_activation: false`, pressed (one `increment`), and text-set (the field holds `24680`), and it never logs `appActive`                                                                                                                                                                                                                              |
| `never`      | `standard`: a target launched off-Space (`CU_FIXTURE_SPACE=auto`, never shown) is listed with `off_space_access: "needs_discovery"` and its observation is refused `off_space_window_unresolved` without `appActive`; `extended`: it is observed with `discovery_activation: true` after exactly one `appActive`, the last activation row is `appInactive`, a coordinate click on `Custom View` logs exactly one `customHit`, and `type_text` leaves exactly `13579`, each ending inactive. `SKIP` for the extended half when the helper reports no discovery or extended delivery |
| `blocked`    | a never-shown target: a wire `look` with `backgroundDelivery: "extended"` and the fixture in `appBlocklist` is refused `app_blocked` (`effectPossible: false`); with `blocked_apps` set, `find_roots` flags the root `blocked` and `off_space` with `off_space_access: "unchecked"` (no accessibility read), `observe_ui` is refused with no `look` reaching the helper, and the fixture never logs `appActive`                                                                                                                                                                    |
| `foreground` | on the `seen` target: a granted wire `act` (`policy: "foreground"`, `foregroundGrant: true`, HID press) is refused `off_space_foreground` with `inputSent: false` and `activationAttempted: false`, nothing is pressed or activated; then `act_ui` with `foreground_grant` covering the fixture sends no foreground act and no `focusWindow`. Run only when `diagnostics.offSpace.available` is true, because a helper without the capability would activate the target and switch the user's Space (`SKIP` otherwise)                                                             |

When no desktop Space of the display is hidden, the run is `SKIP(<reason>)` (exit 0). Exit 0 only for `PASS` or `SKIP`. Output: `<out>/summary.json` (helper capability, display, per-scenario checks with their Space and frontmost details, reduced tool outcomes without outlines or images, front before and after), both request logs, and the fixture logs under `<out>/fixture/`. Scoring is pure in `safety/offspace-score.ts`, tested by `safety/offspace-score.test.ts`.

Off-Space fixture options (off by default; they move only the fixture's own windows, through its own window-server connection): `CU_FIXTURE_SPACE=auto|<space id>` hides the target's windows (alpha 0), moves them to that Space before and right after they are first ordered in, and logs `spaceMove` (request, space, moved, each window's Spaces, every display's Spaces), so they are never shown on a visible Space; `auto` picks a desktop Space of the window's display that the display is not showing (`space: -1` when there is none). A `.cu-space-<instance>` trigger (body `auto` or an id) moves them later, and `.cu-spaces-<instance>` (body: a sequence number) logs `spaces` (`seq`, each window's Spaces, every display's identifier, current Space, and desktop Spaces, and the frontmost pid).

`CU_FIXTURE_SPACE_WINDOWS=<label,...>` (`main`, `second`, `web`) limits `CU_FIXTURE_SPACE` to those windows; the others open where they normally do (default: all).

### Coordination check (`safety/coordination.ts`)

```sh
node packages/choco-pi-computer-use/e2e/safety/coordination.ts --helper-app <dev app> --helper-socket <dev daemon socket> --out <fresh dir> [--cases cancel_wait,expiry_silent,expiry_killed,discovery_hold]
```

Model-free, raw-wire reproductions of four cross-session coordination defects; each case FAILs on a helper that has its defect. It has the same helper checks and refusals as `run.ts` (`HELPER_IS_MAIN`, diagnostics, probe claim), and it takes keyboard focus in the expiry cases.

| Case             | Asserts                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cancel_wait`    | A holds the foreground section; B's `acquire` (with an `acquireId`) waits, then B closes that connection and sends a release naming the id. When A releases, a third session gets the section at once: B's abandoned wait took nothing                                                                                                                                                                                                                                                                        |
| `expiry_silent`  | With the holder frontmost, A acquires the section, makes one granted click on the target's Custom View (HID, which brings the target to the front), and then sends nothing. With no request from anyone, the holder is frontmost with its window key again within 15 s (idle TTL 10 s plus the helper's 3.5 s restore bound plus a 1.5 s margin). B, acquiring afterwards, records the holder as the user's frontmost app, and focus does not change during B's section                                       |
| `expiry_killed`  | The same, with A in a child process that is killed with SIGKILL after its act                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `discovery_hold` | The target's web window is on screen and its main window is on a hidden desktop Space, never shown (`CU_FIXTURE_SPACE=auto`, `CU_FIXTURE_SPACE_WINDOWS=main`). A types 60 digits into the web input with extended delivery while B observes the main window with extended delivery, which needs a discovery activation. Every digit lands in the web input and no key reaches another window; B's look either finishes after A's act or is refused `target_busy`. INCONCLUSIVE if no discovery activation ran |

Exit 0 only when every case is PASS. Output: `<out>/summary.json` (per-case checks and notes), `<out>/requests.jsonl`, and the fixture logs under `<out>/fixture-<case>/`.
