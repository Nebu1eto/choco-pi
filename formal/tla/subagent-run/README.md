# subagent-run: the subagent run lifecycle

A TLA+ model of `AgentManager` in `.pi/packages/choco-pi-subagents/src/agent-manager.ts`: spawn, a run's outcome, usage-limit evaluation, parking and waking at reset, user stop, foreground and background resume, deferred worktree cleanup, result publication, completion delivery and result reads.

## Claims checked

| Invariant            | Claim                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `StopSticks`         | After a user stop (`abort` → `stopRecord(record, true)`) the agent is never running, queued or parked again unless the user explicitly resumes it.                             |
| `PublishOnce`        | Each generation is published at most once, and its completion is delivered (an `onComplete` call, or the inline return of a foreground run) at most once.                      |
| `SettledIsPublished` | A terminal record with no pending run continuation and no pending cleanup callback has published its current generation. With `PublishOnce` this is "completion exactly once". |
| `StaleInert`         | Code acting for a superseded generation never writes the record's outcome (status, result), publishes, or delivers a completion.                                               |
| `ReadSeesFinal`      | A result that was read (`claimSubagentResultRead`) or returned inline is never changed afterwards.                                                                             |
| `ParkedHasWake`      | A `waiting_for_reset` record always has a pending wake: an armed timer or a wake in flight.                                                                                    |
| `PoolExact`          | `runningBackground` equals the number of runs holding a pool slot, and never exceeds the limit.                                                                                |
| `QueueProgress`      | No queued record is stranded while a pool slot is free.                                                                                                                        |
| `TypeOK`             | Sanity bounds on the state.                                                                                                                                                    |

`StaleInert`, `PublishOnce` and `ReadSeesFinal` are checked through history (ghost) variables in `gh`; they are not part of the code.

### What the model leaves out

The `/stop` latch (`isAdmissionOpen`, `requireAdmissionOpen`, `refuseClosedStart`), suspend, dispose, revival and the journal, run budgets (`forcedStatus`), parent abort signals, nested children and `abortOwnedChildren`, workflow and `/btw` records (`canParkForReset` is taken as true), steering, `drainQueue`'s provider-block, repark and start-throws branches, `cancelUsageLimitWaits`, active result reads, and what `recordRunVerdict` does (only its await is modelled). Each await is treated as a point where any other action may run, which admits interleavings the event loop makes rare (a user stop is a macrotask). It never admits fewer.

What a verdict record contains is not modelled: a stop that lands while `recordVerdict` writes (the record is rewritten as `missing`) is checked by `.pi/packages/choco-pi-subagents/tests/verdict-record-stop.test.ts`, not by TLC. The model covers only when publication happens relative to the recording.

The publication change for stopped post-reset continuations also reaches `cancelUsageLimitWaits`, `refuseClosedStart`, `drainQueue`'s start-throws branch and `startRevivedContinuation`'s start failure. The model covers only the `stopRecord` path; the others follow the same rule (the finalizer publishes after the cleanup) and are covered by the package tests, not by TLC.

## Bounds

`SubagentRun.cfg`: `Agents = {a1, a2}`, `MaxConc = 1`, `MaxGen = 3`, `WT = {a1}`, `Full = {a1}`, `VerdictRole = {a1}`.

- Two agents and one slot are the smallest setting with contention: queueing, draining, and a continuation that has to wait.
- `MaxGen = 3` covers a spawn, one post-reset or resume generation, and one more resume after it: the shortest chain behind the dropped-wake defect (park, wake, stop, resume). A wake or resume at the bound is disabled, not wrapped.
- `a1` exercises every caller action (foreground spawn, both resume modes, model switch, reads), spawns with a worktree, and is a verdict-role run, so its settles carry the verdict await. `a2` only spawns and resumes in the background, without a worktree and without the verdict await, and is never read. It is there to hold the slot. Giving `a2` everything multiplied the state space by five and found nothing more.
- Other `VerdictRole` sets were checked once and pass: `{}` 227,992 states, `{a2}` 306,244, `{a1, a2}` 401,371.
- `resume-ignores-publication` uses `MaxGen = 2`: with the guard removed, three generations exceeded 5 million states.

Not covered by these bounds: three or more agents, nested agents, more than one parked record waiting on the same provider.

Size: 18 actions, 8 variables, 230,522 distinct states, depth 54, about 11 s on one TLC worker. (Down from 299,537 when a stopped queued verdict-role run began to notify: its ghost notification count now matches states reached by other paths, so TLC merges them.)

## Environment assumptions

- `EnvCallbackMayThrow = TRUE`: `onComplete` may throw. Every call site contains it now.
- Resumes and result reads may happen at any point, including while a stopped post-reset continuation's worktree cleanup is pending. (An earlier version excluded that window with `EnvActDuringDroppedCleanup = FALSE`; the fix below made the exclusion unnecessary and it was removed.)

## Findings

**Dropped-wake cleanup raced a resume and a read (fixed).** The 14-state trace: `a1` (worktree) parks on a quota limit, the reset is confirmed, its continuation queues behind `a2`, the user stops it. `stopQueuedRecord` published the stopped generation at once, but `settleDroppedWake` deferred `onComplete` until the worktree cleanup settled, and the cleanup appends the "Work retained in worktree" note to `record.result`. In that window a resume was admitted (the generation was published), so the late `onComplete` reported the record while it belonged to the new run, and a result read saw text that changed afterwards. Now `stopQueuedRecord` leaves a post-reset continuation unpublished and `settleDroppedWake` publishes after the cleanup, as `settleParked` does; until then `resumeBlockedByRun` refuses a resume and a read reports `terminal-pending`. Mutation `dropped-wake-publishes-early` restores the old behaviour. `.pi/packages/choco-pi-subagents/tests/model-replay-dropped-wake.test.ts` replays both halves and fails with the fix reverted.

**S2 (an uncontained completion callback on the `.catch` path).** The model expresses it: mutation `catch-callback-uncontained` violates `QueueProgress` in five states. `tests/model-replay-catch-callback.test.ts` replays it. On the branch's base commit it fails (the queued agent stays `queued`); on the current tree, where another change wrapped every `onComplete` call, it passes and is kept as a regression test.

**Redundant checks.** These mutations change nothing within the bounds, so the checks they remove carry no load for these invariants: `survivor-no-inner-eval-checks` (the two `eligible()` checks inside `evaluateUsageLimit`), `survivor-no-eval-return-check` (`evaluateRunUsageLimit`'s final `eligible()`), and `survivor-no-final-gen-check` (the generation check after the verdict point). The caller's `currentUsageDecision` and `resumeBlockedByRun` carry the argument. The inner checks also stop provider closures from being written, which the model does not represent. These configs are not in `check.json`, because a mutation there must fail.

## Running

From the repository root, after `node .pi/skills/formal-verify/scripts/tlc-setup.ts --dir formal/.tools`:

```sh
# base model and every mutation, against check.json
node .pi/skills/formal-verify/scripts/check-all.ts --only subagent-run --tools-dir formal/.tools --jobs 2

# one config
node .pi/skills/formal-verify/scripts/tlc.ts check --spec formal/tla/subagent-run/SubagentRun.tla \
  --config formal/tla/subagent-run/mutations/no-caller-recheck.cfg --tools-dir formal/.tools \
  --max-states 2000000 --timeout-ms 180000
```

The full set takes about 140 s with `--jobs 2`. The replay tests run under `node --test` like any package test; `model-replay-settle-hops.test.ts` pins how many microtask turns a non-verdict run's settle takes.
